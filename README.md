# 风神考核看板（Chrome 扩展 · 通用版）

风神页面常驻**一颗「看板」总按钮**：点开是一个小菜单，里面有两个互不干扰的功能入口 —— 「**考核看板**」（规划单量完成率、标 2 骑手占比、考核得分、时段 × 商圈片达成矩阵）与「**出勤达成**」（应排 / 实排 / 有效出勤、实排达成 / 应排达成）。两个入口各打开一个独立页面、各导一张图；功能分开，但入口收拢到同一个按钮里，页面上不再散落多颗悬浮球。全部数据在本机浏览器内获取，跟随当前浏览器登录态，换账号自动换商，无需本地服务、无需 Python。

从 **v3.2.0** 起支持从本 GitHub 仓库自动检查与更新新版本（v3.3.2 增加实时备用版本源，v3.3.3 起「检查更新」无论有无新版都会明确反馈结果）；从 **v3.3.0** 起运单改为增量同步，刷新不再重拉当日全量明细；v3.3.4 起把「接口运单总数」与「实际完单」分开标注，避免把配送失败单误看成完单；v3.3.5 起增量同步改用「运单终态时间」水位并定期做状态回写校准；**v3.3.6 起标2 / 完单达标骑手只算「非人工改派」完成单**；**v3.4.0 起工具条增加「复制图片」，一键把看板复制为高清 PNG**；**v3.4.1 起时段矩阵不再硬编码 7 个班次，改为按当日排班实际班次动态生成**；**v3.4.2 起字体统一为系统默认 UI 字体，班次变多不再把表格压成 10/11px 小字**；**v3.4.3 起取消「每 30 分钟强制全量校准」，改为滚动分片状态校准，接口入库延迟也不再降级全量，日常刷新稳定走增量**；**v3.5.0 起新增「出勤达成」：应排 / 实排 / 有效出勤，以及实排达成、应排达成两张动态时段宽表**；**v3.6.0 起该功能拆到独立入口与独立页面，原考核看板恢复为纯净版本，两边互不干扰**；**v3.7.0 起出勤达成可选择日期（含「今天 / T-1」快捷按钮，可回看最近 90 天），历史日期改走「出勤统计 → 导出明细数据」的骑手时段明细，全天达成忽略系统给出的错误标记、按有效在线 ≥6 小时且完单 ≥18 单手工判定**；**v3.7.1 起日期框两侧加了左右箭头，可逐日快速切换，到「今天」或「90 天前」边界自动置灰**；**v3.8.0 起原「考核看板」也能选日期（同一套日期控件）**；**v3.9.0 起考核看板不再同步运单 —— 完单量直接取「出勤统计」的骑手全天完单，刷新从「上百页运单」降到「排班 + 考勤」两个导出请求，秒级出结果且与考核系统同源**；**v3.10.0 把「人工改派剔除」补回来 —— 只按 `isReassign=1` 单独查改派单（通常两三页）后从骑手达标扣减，完单仍取自考勤统计，速度和口径两不误**；**v3.11.0 起出勤达成可以点单元格看「炸班」明细 —— 排了班但没达到有效出勤的骑手，逐个给出姓名、有效在线、完单和未达标原因**；**v3.12.0 起「实排达成 / 应排达成」收成一组页签，一次只看一张表，点一下换分母（选择记在本机）**；**v3.13.0 起页面下方给出「炸班明细」全量清单 —— 按班次分行，列出当天所有排了班但没达标的人（姓名 / 站点 / 有效在线 / 完单 / 原因，两项指标各带绿 ✓ 或红 ✗）；今天只显示已结束的班次，未跑完的不参与统计**；**v3.13.1 起今天的炸班明细默认不显示「全天」—— 一天没过完，按 6h / 18 单判「全天未达标」不准；清单标题右侧留了一个开关，默认关、想粗略看可手动打开（选择记在本机），达成矩阵的全天列和顶部「整商全天」概览保持不变**。

## 安装

1. 到 [Releases](https://github.com/hubiqi/fengshen-ext/releases/latest) 下载最新的 `fengshen-ext-vX.Y.Z.zip`，解压到一个**固定、不会移动**的目录（例如 `~/Extensions/fengshen-ext`）。
2. 打开 `chrome://extensions`，右上角开启「开发者模式」。
3. 点「加载已解压的扩展程序」，选择刚才解压的目录。

> 环境要求：Chrome / Edge **111 及以上**（service worker 使用 ES module 与 Promise 风格扩展 API）。
> 已在风神页面登录的前提下，点击页面右侧的「看板」总按钮，在菜单里选「考核看板」或「出勤达成」；也可点浏览器工具栏图标直接展开/收起面板。

## 两个独立入口（v3.6.0）

「新增功能不要混进原功能入口，但两个入口别散落在页面上」——v3.6.0 把出勤达成从考核看板里完整拆出来，同时用**一颗总按钮**把两个入口收在一起：

- 菜单会贴着按钮弹出（靠右时向左展开、靠左时向右展开，始终留在可视区内）；点页面空白处或按 Esc 收起菜单，再按 Esc 收起面板。
- 面板顶部另有「**考核看板 / 出勤达成**」页签可直接互切，两个 iframe 各自保留状态，切回来不会重新拉数。

| | 「考核看板」入口 | 「出勤达成」入口 |
| --- | --- | --- |
| 总按钮菜单项 | 蓝色「考核看板」 | 绿色「出勤达成」 |
| 页面 | `dashboard.html` | `attendance.html` |

| 取数 | **排班 + 考勤 / 出勤明细**（v3.9.0 起不再同步运单） | **只拉排班 + 考勤**，不拉运单明细、不写运单缓存 |
| 「复制图片」 | 只导出原考核看板 | 只导出出勤达成当前页签那张表 + 下方炸班明细（含「全天」开关状态），文件名 `风神出勤达成_YYYYMMDD.png` |
| 刷新 / 通道 / 纯净模式 | 各自独立 | 各自独立 |

- 面板右上角「**新标签打开**」按当前页签打开对应页面；出勤页工具条的「**考核看板 ↗**」可一键切回原看板页签（独立标签页则新开一个标签）。
- 浏览器工具栏图标点击时直接展开/收起面板（默认沿用上次打开的功能），不经过菜单。
- 入口与画面完全分开后，原考核看板的标题、底部口径、导出的 PNG 都与 v3.4.3 一致，不再出现出勤相关的表或开关。

## 完单直接取自考勤统计（v3.9.0）

「骑手根本不需要同步运单」——出勤统计本来就是 **骑手 × 时段** 粒度，每行同时带着「有效在线时长」和「完单量」，全天行再给出全天合计。所以考核看板的完单量现在直接从这里读，不再分页拉运单。

| 指标 | v3.8.0 及之前 | v3.9.0 起 |
| --- | --- | --- |
| 实际完单 / 时段完单 / 骑手完单 | `queryTracking/2.0` 分页拉运单，逐单判 `stateDesc` 是否「配送成功」 | 出勤统计的「全天」行 / 时段行的 **完单量** |
| 每次刷新请求数 | 几十～上百页（90 条/页 + 1.2s 节流），历史日期 1–3 分钟 | **2 个导出请求**，通常 2–5 秒 |
| 本地缓存 | `wb_orders_current` 存当日运单，跨天/换商失效 | 不再写运单缓存，只记一份 `teamIds` |
| 口径一致性 | 自己按状态位判成功单 | 与考核系统同一个数据源 |

### 为什么口径能对上

用 2026-11-06 真实数据逐单对账：整天运单 **9345 单**，其中「配送成功」**9051 单**；出勤统计的全天完单合计**也是 9051 单**，而且**逐骑手 233/233 完全相等，偏差 0**。也就是说：

> 出勤统计的「全天完单量」= 运单里 `state=40 配送成功` 的单数，一分不差。它本身就是考核系统的结算口径。

原先以为的「0.7% 差异」只是把运单总数（含配送失败）跟完单数混在一起比了；按成功单比，两边完全一致。这也直接说明了一件事：**出勤统计没有剔除人工改派**，这正是 v3.10.0 要补的（见下一节）。

> 同一天同一套排班，v3.10.0 算出的规划单量 9386、实际完单 9051、完成率 96.4%、完单达标 206、标2 206、应排 231、标二占比 89.2%、考核得分 85.2；出勤达成的 231 / 232 / 224 与改造前完全一致。

### 站点范围只识别一次

导出接口传 `teamIds: []` 会返回「没有该团队的数据权限」，所以必须带站点 ID。取法按代价从低到高：

1. `localStorage` 里记住的 `wb_team_ids_v1`（**0 请求**，日常刷新都走这条，两个页面共用）；
2. 旧版留下的运单缓存（**0 请求**，只读 `teamId`，用于从 v3.8 平滑迁移）；
3. 实在没有才查 **1 页运单**（1 请求，只为拿 `teamId`）。

换账号 / 站点增减后站点范围会变，点工具条的「**重识站点**」清掉缓存重拉即可。

### 标2 口径：只查改派单，把剔除补回来（v3.10.0）

v3.9.0 为了省掉运单同步，顺手把「人工改派剔除」也丢了 —— 当时以为出勤统计已经按结算规则统好，实测发现并没有（见上一节：9051 = 9051，一分没剔）。KPI 第十三条要求**改派完单量在标 1–标 5 中剔除**，所以这一步必须补。

关键在于：不用为了拿改派单去拉全量运单 —— `queryTracking/2.0` 支持 `isReassign` 直接筛选。

```js
// dashboard.js
buildQueryPayload(page, undefined, undefined, date, { isReassign: 1, teamIds })
```

实测 11-06 全天 9345 单里，改派单只有 **159 张**（2 页就取完），其中配送成功 **149 张**。于是整商的取数变成：

| 请求 | 次数 | 用途 |
| --- | --- | --- |
| `exportSchedule/1.0` | 1 | 规划单量 / 应排人数 / 时段预估 |
| `exportAttendance` 或 `exportStatisticsDetail` | 1 | 完单量 + 有效在线时长 |
| `queryTracking/2.0`（`isReassign=1`） | 2～4 | **只拿改派单名单**，用于剔除 |
| `queryTracking/2.0`（无条件） | 0～1 | 仅首次识别 `teamId`，之后走缓存 |

仍然是秒级，没有回到「上百页运单」。

处理细节：

- **只剔「配送成功」的改派单**。改派了但最终取消 / 失败的单本来就不算完单，再扣一次就多扣了（11-06：159 张里 10 张未送达，不参与剔除）。
- **只动骑手达标口径**。片区「实际完单」、订单完成率、时段完单仍是考勤原值（含改派单），与 KPI「只剔除标 1–标 5」一致。
- **扣减后钳到 0**，不会出现负数达标。
- **`null` 与 `[]` 严格区分**：`reassignOrders` 是 `null` = 改派查询失败，此时**不剔除**并在底部写明「本次未取到改派单」，宁可显示偏高的人数也不静默少扣；`[]` = 查过了、当天确实没有改派。

> 11-06 实际影响：完单达标 208 → **206**，标2 208 → **206**，2 人因改派单跌破门槛。
>
> ⚠️ 标二占比跟着从 **90.04% 掉到 89.18%**，而考核得分对标二占比是**台阶函数**（≥90% 满分 100，80–90% 线性 80–90 分），跨过 90% 这条线后得分从 **91.7 → 85.2**。这不是算错了，是剔除改派后本来就该有的结果 —— 之前的高分是被改派单抬上去的。

如果哪天真要完整复核，`ASSESS.build(orders, sch, att, date, XLSX)` 仍保留**全量运单口径**（传非空 `orders` 即生效），与「考勤 + 改派单」应当得到同一组人数。

### `sync.js` 还在，但只做迁移

运单增量同步（终态时间水位、滚动分片校准、对账续补）的代码原样保留在 `sync.js` 里 —— 两个页面仍会用它**只读**旧缓存里的 `teamId`（0 请求完成站点范围迁移），除此之外不再调用。看板进度条也不会再出现「增量 / 全量 / 水位」之类的字样。

### 运单口径：拉取总数 ≠ 实际完单（历史说明）

v3.8.0 及之前看板按运单统计完单时，`queryTracking/2.0` 的 `total` 是**当日全部运单**，包含「配送失败」单（实测 `state=40 / 配送成功`、`state=90 / 配送失败`，某日首页 90 单里就有 2 单失败）。旧版会在进度条里把「拉取 N 单（配送成功 x · 配送失败 y）」与「实际完单」分开标注，避免把失败单误看成完单。v3.9.0 起完单改由出勤统计给出，这套拆分文案不再出现；保留此段是因为：万一你通过 `ASSESS.build(orders, …)` 走运单口径复核，规则仍然是**只算配送成功、失败单从不计入**。

### 标2 骑手口径：剔除人工改派完单（v3.3.6）

KPI 第十三条「人工改派结算限制」：**改派完单量在标 1–标 5 中剔除** —— 系统已指派骑手后，站长手动把订单改派给新骑手，这类完成单不计入该骑手的运力达标标准。

`queryTracking/2.0` 每条运单带 `isReassign` 字段（`0` / `1`，实测某日首页 90 单里有 3 单为 `1`，且都是配送成功单）。v3.3.6 起 [`assess.js`](./assess.js) 的处理：

| 指标 | 口径 |
| --- | --- |
| **完单达标人数 / 标2 骑手数** | 只累计「配送成功 **且** `isReassign != 1`」的单；门槛仍是 UB≥26 / 其他≥24，标2 另需全天有效在线时长≥6h |
| **片区实际完单 / 订单完成率 / 时段完单** | **不变**，仍按全部配送成功单统计 —— KPI 只规定标1–标5 剔除，规划单量完成率不在此列 |
| 判定兼容性 | 同时兼容 `isManualReassign` / `reassignFlag` 等可能的字段名；字段缺失、为 `0`、为「否」一律按未改派，宁可少剔除也不误判达标骑手 |

看板底部会写出本次剔除量与影响，便于对账，例如：

```
标2口径：人工改派成功单 3 单已从骑手达标统计剔除（完单达标 128→126、标2 96→95，2 人因此跌破门槛）；片区实际完单仍含改派单
```

> **已知限制**：KPI 条款还规定「卡餐单、兜底单、养老餐改派单可计入完单」，但这三类例外需要出餐时间 / 兜底标记 / 业务品类等额外数据，当前运单接口只有 `isReassign` 一个布尔位，无法区分人工改派与这些例外，因此 v3.3.6 **对所有改派成功单一律剔除**。若结算需要对例外单放行，需另外接入能识别例外类型的数据源，再在 `isReassigned()` 里加白名单。

## 一键复制图片（v3.4.0）

看板工具条的「**复制图片**」按钮会把 `#sheet`（即 1:1 复刻钉钉考核看板的那块画面）渲染成一张 **1240px 宽、2 倍像素密度的 PNG**，写进系统剪贴板，随后可直接 `Ctrl/⌘+V` 粘贴到钉钉 / 微信 / 文档里。

- **只截看板画面**：不含工具条、更新提示、进度条、播报区和底部元信息；与原先「纯净看板 + 系统截图」看到的内容一致。
- **固定桌面版排版**：导出时忽略响应式 `@media` 规则，固定按 1240px 逻辑宽度出图。即使看板浮层很窄、屏幕上是「手机排版」，复制出来的图仍是钉钉下发的那张宽表，不会换行或截断。
- **纯本地、零依赖**：[`capture.js`](./capture.js) 用 `SVG foreignObject + Canvas` 实现，不引入 html2canvas / dom-to-image 之类的第三方库，不发起任何网络请求，业务数据不出浏览器。
- **失败自动降级**：剪贴板不可写（权限策略、浏览器版本、页面失焦等）时，自动下载同名 PNG 文件，仍可拖进钉钉 / 微信；按钮下方会明确写出实际结果（已复制 / 已另存 / 已自动下载）和图片尺寸。
- **按住 Shift 点击**：直接另存为 `风神考核看板_YYYYMMDD.png`，适合归档或需要原图的场景。
- **两个入口各导各的图（v3.6.0）**：原考核看板只截 `#sheet` 的考核画面；独立出勤页只截自己的两张达成表，另存为 `风神出勤达成_YYYYMMDD.png`，不会把新表混进原来的看板图。
- **文件名跟所选日期走（v3.7.0）**：出勤页选了 T-1 或更早日期，PNG 文件名与画面里的日期都用所选日期，不会误写成今天。

实现上，`ClipboardItem` 里放的是 `Promise<Blob>`，因此 `navigator.clipboard.write()` 在点击的同一个任务内就发起，PNG 渲染再慢也不会丢掉 Chrome 要求的 transient user activation。manifest 额外声明了 `clipboardWrite`（MV3 有效、无安装警告），看板 iframe 也显式带 `allow="clipboard-write *"`，两者共同保证在风神页面浮层里同样能复制成功。

## 时段矩阵按排班动态生成（v3.4.1）

旧版在 `assess.js` 里**硬编码了 7 个工作班次**（早餐2 / 午高峰 / 下午茶1 / 下午茶2 / 晚高峰 / 夜宵1 / 夜宵2），但排班表里的班次数是按天、按合作商变化的。实测 `data/raw/` 的真实排班统计表：

| 排班文件 | 「时段」列取值 | 工作班次 |
| --- | --- | --- |
| `排班数据_20261031.xlsx` | 休息、早餐2、午高峰、下午茶1、下午茶2、晚高峰、夜宵1、夜宵2、全天 | 7 个 |
| `排班数据_20261105.xlsx` / `1106` | 上面 **+ 凌晨1 + 早餐1** | **9 个** |

旧版第 `PERIOD_NAMES.includes(per)` 这一句会把「凌晨1」「早餐1」直接丢掉：这两列的**预估单量不进矩阵**，00:00–08:00 的完单也因为 `periodOf()` 只认 7 个时间片而全部不计入时段矩阵 —— 这就是「时段不全」。

v3.4.1 的处理：

1. **先解析排班，再定口径**：`ASSESS.build()` 内对排班统计表做两遍扫描 —— 第 1 遍只读当天出现过的班次名（排除「全天」「休息」），第 2 遍才按这批班次累加规划单量 / 应排人数 / 时段预估单量。时段矩阵的列、运单时间归类、合计行全部共用这一份 `periods`。
2. **班次时间区间来自 KPI 标准**：排班表只有班次名、没有时间范围，运单接口也只有 `completeAt` / `trackingFinishAt` 时间戳。因此 `assess.js` 内置了与 `config.py` 的 `PERIOD_STANDARDS` 逐行对齐的 **11 时段字典**（凌晨1 00:00-02:00、凌晨2 02:00-04:00、凌晨3 04:00-06:00、早餐1 06:00-08:00、早餐2 08:00-10:30、午高峰 10:30-13:30、下午茶1 13:30-15:30、下午茶2 15:30-17:30、晚高峰 17:30-20:00、夜宵1 20:00-22:00、夜宵2 22:00-24:00），按时间先后输出当天排班里出现的班次。
3. **未排班时段的完单**：只计入「实际完单」和完成率，**不进时段矩阵**，矩阵与排班严格一一对应。例如 11-06 排了「凌晨1」但没排「凌晨2 / 凌晨3」，则 02:00–06:00 的完单不会出现在任何时段列。
4. **排班取不到时兜底**：回退到旧版的 7 个默认班次，看板底部会写明「排班未取到故回退默认 7 班次」，不会静默用错口径。
5. **表格宽度**：表 2 总宽固定 1218px，班次变多时**压缩子列宽**（7 班次 72px、9 班次 56px、11 班次 45px），而不是把表格撑到 1506px —— 这样「复制图片」的 1240px 画布不会被裁切。v3.4.2 起字号不随列宽缩小：一级表头是 `colspan=2`（最窄也有 90px），完全放得下 4 字班次名，正文与二级表头始终保持常规字号。

看板底部会列出本次时段口径，例如：

```
时段矩阵：按当日排班 9 个班次动态生成（凌晨1 / 早餐1 / 早餐2 / 午高峰 / 下午茶1 / 下午茶2 / 晚高峰 / 夜宵1 / 夜宵2）；落在未排班时段的完单不计入矩阵，但仍计入实际完单
```

> **为什么没有真的把排班请求挪到运单之前**：`exportSchedule/1.0` 的 `teamIds` 是从运单明细里收集的站点 ID，强行提前且传空数组可能拿不到全量排班。而 `ASSESS.build(orders, schSheets, attSheets, …)` 本来就是一次性拿到三份数据再计算，所以「先知道有哪些班次」在 `build()` 内先解析排班即可实现，效果相同且不破坏取数依赖。
>
> **未识别班次**：若排班出现了字典里没有的新班次名，它无法做时间归类，不会进矩阵，但预估单量仍计入「规划单量」；看板底部会点名提示，需要把新班次补进 `PERIOD_DEFS`。

## 出勤达成：应排 / 实排 / 有效出勤（v3.5.0，v3.6.0 起独立入口，v3.7.0 起可选日期）

「出勤」入口打开的是一张独立的看板，含两块「商圈片 × 时段」达成矩阵（v3.12.0 起收成一组页签，一次看一张）：**上方百分比 + 下方「有效出勤/分母」**，配色为 ≥100% 绿、80–99.9% 橙、<80% 红。

| 指标 | 数据来源 | 口径 |
| --- | --- | --- |
| 应排 | 排班统计 `应排人数` | 按站点→商圈片、按当天时段求和；「全天」取排班统计的全天行 |
| 实排 | 排班统计 `排班人数` | 同上，即实际排上班的人数 |
| 有效出勤 | 实时考勤（今天）/ 出勤统计时段明细（历史日期） | `排班状态=排班` 且（**时段有效在线时长 ≥ 该时段标准** 且 **时段完单量 ≥ 该时段标准**）的去重骑手数；全天按 6h / 18 单 |
| 实排达成 | 有效出勤 ÷ 实排 | ≤100%（有效出勤是实排的子集） |
| 应排达成 | 有效出勤 ÷ 应排 | 可 >100%（多排班不设上限），例如凌晨1 `4/1 = 400%` |

时段标准与 `config.py` 的 `PERIOD_STANDARDS`（KPI PDF 第 9-10 页）逐项对齐：凌晨1 90 分钟/1 单、早餐1 90/1、早餐2 120/1、午高峰 150/5、下午茶1 90/2、下午茶2 90/2、晚高峰 120/3、夜宵1 90/2、夜宵2 90/2；「全天」按运力标准 1 等效的 **6 小时 / 18 单**。列同样按当天排班实际班次动态生成（全天 + 7/9/11 班次），总宽锁 1218px，字号保持常规，不撑破「复制图片」的画布。

- 顶部三数概览直接给出整商全天的 **应排 / 实排 / 有效出勤** 与两个达成率；鼠标悬停任意格子会显示该格三个数。
- **今天的考勤是实时快照**：还没结束的班次若暂时无人达标，显示「统计中 / 未开始」而不是误报 0%，当晚继续刷新或次日查看会自然补齐；**历史日期是定稿数据，不再显示「统计中」**。
- 独立页面自带「日期 / 今天 / T-1 / 立即刷新 / 复制图片 / 通道 / 纯净看板 / 考核看板 ↗」；5 分钟自动刷新只对「今天」生效，历史日期不重复拉取；**不拉运单明细、不写运单缓存**，站点 ID 优先复用原看板已落盘的运单缓存（0 次额外请求），缓存不存在时只查运单第 1 页（1 次请求）。
- 排班统计或考勤任一侧缺关键列时，页面会点名提示并**不渲染两张空表**，不会把空表塞进 PNG；若考勤导出缺「完单量」列，则降级为只看有效在线时长并明确标注。
- **日期选择的完整口径见下一节**。

> 口径已用 2026-11-06 真实排班 / 考勤 xlsx 与两张截图逐格对账：应排、实排共 60 个分母完全一致，白天 40 个有效出勤分子完全一致；截图里的「全天」「夜宵2」分子来自当天结束后的完整快照，本地 22:10 导出的考勤快照会略小，属预期差异。

### 点单元格看炸班明细（v3.11.0）

「炸班」= 当天排了班（`排班状态 = 排班`），但当班次没达到有效出勤标准的骑手。他们既算不进「有效出勤」，又占着「实排」名额，是达成率掉下来的直接原因 —— 所以要看得到是谁。

- 点实排达成 / 应排达成表里的**任一格子**（团队 × 时段，含「全天」列），弹出该班次的炸班骑手清单：**姓名（附骑手 id）/ 站点 / 有效在线 / 完单 / 未达标原因**。
- 原因分四类：`未出勤`（有效在线与完单都是 0）、`时长·完单均不足`、`有效在线不足`、`完单不足`；清单按有效在线升序，最差的排最前，未出勤用浅红底标出。
- 弹窗副标题直接给该格的 **应排 / 实排 / 有效出勤 / 实排达成** 与该班次的判定标准（例如「有效在线 ≥1 小时 30 分 且 完单 ≥2 单」）。
- 两者关系恒成立：**有效出勤 + 炸班 ≈ 实排**（两套表口径允许 ±2 人）。11-06 对账：实排 232、有效出勤 224、全天炸班 8 人；全商炸班 27 人次 / 13 个格子，逐人（姓名、有效在线、完单）与原始明细完全一致。
- 关窗支持右上角 ×、点遮罩、Esc 三种；**Esc 先关弹窗**，不会把整个看板面板一起关掉。
- 弹窗挂在 `#sheet` 之外，**「复制图片」永远只导两张表，不会把弹窗截进去**；单元格只加 hover 底色与手型光标，静态版式、导出图与之前完全一致。
- 查历史日期时清单是定稿的；查今天（实时快照）时，未结束班次里「还没跑满」的骑手也会列出 —— 弹窗顶部会明确提示「该班次尚未结束，可能还在补齐」，别当定论。
- 明细口径以考勤表「排班状态 = 排班」为准，与排班统计的「排班人数」来自两张不同的表，人数可能差 1–2 人，弹窗里也写明了这一点。

### 实排 / 应排 页签切换（v3.12.0）

两张表的分子是同一份「有效出勤」，只有分母不同（实排 = 排班人数，应排 = 应排人数），并排竖着放等于把几乎一样的数字滚两遍。v3.12.0 把标题下方改成一组页签，**一次只看一张表**：

- 标题下方是「**实排达成 ｜ 应排达成**」两个页签，默认看实排达成；点另一个换分母，表格内容与配色随之切换。
- 切换**只改显示**：不重新取数、不重算口径，两张表在切换前都已渲染好，点了即刻生效（取数与切页签互不影响）。
- 选择记在本机（`localStorage` 的 `wb_att_view`），下次打开出勤页还是上次看的那张；页签也可以用键盘 ← → 切换。
- 页签在 `#sheet` 内，**「复制图片」导出的 PNG 也能看出当前看的是哪个口径**；表标题里的分子分母与页签一致，贴到群里不会看错。
- 概览区仍同时给出两个达成率（`实排达成 / 应排达成`），只有矩阵收成一张 —— 想看另一个分母点一下即可，不用再截两张图。
- 「炸班明细」在两张表里都能点开，格子与口径不受页签影响。

#### T0 只显示已结束的班次（v3.13.0）

今天查实时快照时，**还没跑完的班次不进表也不算炸班**——人还在陆续上线、单还在攒，这个时点判定「不达标」既不公平也没意义（11-06 晚 20 点看快照，夜宵2 有 84 人才刚上线 10 分钟、0 单，全被算成炸班）。

| 场景 | 矩阵列 | 炸班清单 |
| --- | --- | --- |
| 今天（T0） | 全天 + **已结束**的班次 | 只列已结束班次的人，**默认不含「全天」**（见下一节） |
| T-1 及更早 | 全天 + 全部班次（定稿） | 全部班次，含「全天」行 |

- 判定「已结束」用班次时间窗：`当前时间 ≥ 该班次 end`（凌晨1 00–02 点、早餐1 06–08 点……夜宵2 22–24 点），全天列始终保留。
- 页面口径说明会点名「今天只显示已结束的班次」，底部元信息还会写「…（夜宵1、夜宵2 进行中）」并在炸班人次后注明「另有 N 人次暂不计入：全天 … + 未结束班次 …」，不会让人误以为漏人。
- 班次一结束，下次刷新（5 分钟自动刷新）就会自动出现在表里和名单里，不需要手动切换日期。
- 同一份 11-06 数据：实时快照（夜宵1/2 未结束）清单 21 人次，定稿（查 11-06 历史日期）是 110 人次 / 27 人次两种口径都能对上——差别全在没跑完的班次。

#### T0 清单里的「全天」默认关闭（v3.13.1）

「还没结束不准」——班次可以等它跑完，但**全天永远要等到这一天过完**才准。今天 20 点时按「有效在线 ≥6 小时 且 完单 ≥18 单」去判「全天未达标」，把还在路上、单还在攒的人列成炸班，名单看着很吓人其实是假阳性。所以 T0 的炸班明细**默认把「全天」整段关掉**：

| | 今天（T0） | T-1 及更早 |
| --- | --- | --- |
| 炸班清单的「全天」横幅 | **默认不显示** | 照常显示（定稿数据） |
| 达成矩阵表头的「全天」列 | 保留，不变 | 保留 |
| 顶部「整商全天」概览 | 保留，不变 | 保留 |
| 清单标题右侧开关 | 显示，默认关 | 隐藏（不需要） |

- **开关**：标题右侧 `☐ 显示全天（未结束，不准）`，点一下变琥珀色勾选态，全天横幅和它下面的人立刻出现；再点一下关掉。切换**只重画清单，不重新取数**，选择写在 `localStorage.wb_att_roster_day`，刷新页面后沿用。
- 用按钮 + `role="switch"` / `aria-checked` + CSS class 表达状态，而不是原生 `<input type=checkbox>`：`foreignObject` 克隆生成导出 PNG 时表单控件的勾选态容易丢，按钮的文字与底色一定能带进图里。
- 打开后说明会写「「全天」为手动打开：今天还没结束，这批人仅供参考」；标题去掉「不含全天」后缀；底部元信息里的「暂不计入」人次同步减掉全天那部分。
- 关掉时清单标题补 `· 不含全天`，说明里点明「今天还没过完，按 6h / 18 单判「全天未达标」不准，N 人次暂不列入」，底部另写「另有 N 人次暂不计入：全天 … 人次（今天未结束，默认关闭）+ 未结束班次 … 人次」，不让人误以为漏统计。
- **清早边界**：如果连一个已结束班次都还没有、全天又被关掉，清单不会整块消失，而是留一句「已结束班次暂无炸班」的空态——否则开关也跟着被藏起来，用户就点不回来了。
- 全天人次从来不参与两张达成表的计算，这里只是**名单的显示口径**；想看准的全天名单，等第二天切到历史日期即可。

## 选择日期：T-1 与历史时段明细（v3.7.0）

出勤页工具条新增 **日期选择器** + **「今天」「T-1」** 两个快捷按钮 + 数据源标签（「实时快照」蓝 / 「历史明细」绿）。可选范围是最近 **90 天（含今天）**，选择会记在浏览器本地，下次打开沿用；工具条上的日期也会被写进两张表的标题、画面副标题、底部口径与导出的 PNG 文件名。

| 所选日期 | 排班统计 | 有效时长 / 完单量来源 | 自动刷新 |
| --- | --- | --- | --- |
| 今天 | `exportSchedule/1.0` | `exportAttendance/1.0`（当日实时考勤快照） | 5 分钟 |
| T-1 及更早 | `exportSchedule/1.0`（支持历史日期） | `exportStatisticsDetail/1.0`（出勤统计 → 导出明细数据） | 关闭（定稿数据） |

**左右箭头逐日快切（v3.7.1）**：日期框两侧各有一颗 ‹ / › 箭头，点一次往前 / 往后挪一天，比打开日历挑日期快得多。切换复用同一套日期校验：到**今天**时右箭头自动置灰（未来没有数据），到**90 天前**时左箭头自动置灰，鼠标悬停会说明原因；边界上的箭头点了不会有任何反应，也不会弹「越界」提示。箭头是用 CSS 画的 chevron，不依赖系统字体里的 ‹ › 字形，Windows / macOS 观感一致；它属于工具条，**不会被截进导出的 PNG**。

**为什么历史日期必须换数据源**：实测 `exportAttendance/1.0` 会**忽略** `startDate` / `endDate`，传 11-02、11-05 都返回当前这一刻的实时快照，拿它算历史出勤等于把今天的数据当成昨天。正确来源是风神「[出勤统计](https://aeolus.ele.me/?targetId=54332#/group/schedule/attendance-statistic)」页的「导出明细数据」：

```js
// 一次请求拿回所有骑手 × 时段的明细，返回 xlsx 下载链接
const API_ATT_DETAIL = "https://httpizza.ele.me/xtop/" +
  "xtop.fs.special.examine.exportStatisticsDetail/1.0";
// 入参必须是 teamIds 数组（传 teamId 会报「查询参数错误」）
{ teamIds: [...], startDate: "2026-11-06", endDate: "2026-11-06" }
```

明细 xlsx 每行是「骑手 × 时段」，含 `站点名称`、`骑手ID`、`考勤日期`、`时段`、`是否排班`、`有效在线时长`、`完单量`，另有「全天」汇总行。[`assess.js`](./assess.js) 的 `ASSESS.detailToAttendance(detailSheets, dateStr, XLSX)` 先扫「全天」行取到每人当日的有效在线时长 / 完单量，再把它摊到该骑手每一行，标准成与实时考勤完全相同的 8 列：

```js
["站点名称", "骑手id", "排班状态", "时段",
 "全天有效在线时长", "全天完单量", "时段有效在线时长", "时段完单量"]
```

之后仍由 `ASSESS.build()` 用**同一套口径**计算，只是换了输入源 —— 不另写一套历史口径，避免两边漂移。

**全天达成标记不可信，一律手工判定**：明细表里全天行的「目标完单量 / 目标在线时长」为空，系统给的「是否达成」并不是按运力标准算的。用 2026-11-06 真实明细核对：

| 判定 | 全天有效出勤人数 |
| --- | --- |
| 直接采信系统「是否达成=达成」 | **205** |
| 按「有效在线 ≥6 小时 且 完单 ≥18 单」手工判定 | **224** |

差 21 人。因此 `detailToAttendance()` **根本不输出「是否达成」列**，`build()` 也只认原始时长与完单量：全天走 `DAY_ATTEND_STANDARD = { timeMin: 360, orders: 18 }`，时段走 `PERIOD_DEFS` 各自的 `timeMin` / `orders`。系统标记在任何链路里都不参与计算。

其他行为：

- **站点 ID 必须有**：历史明细接口要求 `teamIds`，页面优先从所选日期 / 今天的运单缓存里收集（0 次额外请求），缓存缺失时只查运单首页（1 次请求）；两者都拿不到会明确提示「请先打开一次考核看板」，不会静默发空数组请求。
- **历史数据不重复拉**：同一日期的排班 / 明细会缓存在内存里，切回来秒回；「立即刷新」强制重拉。历史日期是定稿数据，5 分钟自动刷新会跳过、复选框也会置灰。
- **文案随模式切换**：历史日期的口径说明会写明「取次日定稿的时段明细」「忽略系统的是否达成标记，按 6h / 18 单手工计算」，不再出现「统计中 / 未开始」。
- **导出图用所选日期**：文件名 `风神出勤达成_YYYYMMDD.png`（例如 `风神出勤达成_20261106.png`），标题、副标题、表头日期同步。

> 11-06 历史明细回归：1645 行 / 351 名骑手，全天应排 231、实排 232、有效出勤 224；五个商圈片全天有效出勤 57 / 38 / 44 / 52 / 33 与截图逐格一致，白天 8 个时段与实时快照一致；11-05 另用独立排班 + 明细单独回归，确认不是复用今天的快照。夜宵2 在 22:10 的实时快照里是 0 人，历史定稿为 80 人 —— 这正是「选 T-1 看定稿」的价值。

## 考核看板也能选日期（v3.8.0）

原「考核看板」工具条也有「日期 + ‹ / › 箭头 + 今天 / T-1 + 数据源标签」，可回看最近 **90 天**（含今天），到边界自动置灰。两个页面的日期**各自独立保存**（`wb_assess_date` / `wb_att_date`），在考核看板切到 T-1 不会影响出勤达成页。

### T-1 的取数与 T0 不同

最容易踩的坑：T-1 不是「把今天的快照换个日期标签」。v3.9.0 之后只剩两处数据源要换：

| 数据 | T0（今天） | T-1 及更早 |
| --- | --- | --- |
| 排班 | `exportSchedule/1.0`：今天 ~ 明天 | 所选日 ~ 次日（实测导出含两天的排班统计，`build()` 按所选日期过滤） |
| 考勤 / 完单 | `exportAttendance/1.0`：当日实时快照（含全天 / 时段完单量） | `exportStatisticsDetail/1.0`（出勤统计 → 导出明细数据）的骑手 × 时段明细，经 `detailToAttendance()` 标准成同款 8 列 |

第二行是硬要求：`exportAttendance/1.0` 实测**会忽略 `startDate/endDate`**，传任何历史日期都返回当前实时快照，所以历史日期必须换接口。历史明细标准化后仍由 `ASSESS.build([], sch, att, 所选日期, XLSX)` 用**同一套口径**计算；全天仍按 6h / 18 单手工判定，不采信系统的「是否达成」标记。

### 历史日期的结果只放内存

- 结果放进**内存 memo**（按 `日期 + 通道`），切回同一天秒回；「立即刷新」强制重拉；
- 关闭 5 分钟自动刷新（定稿数据不会变），工具条复选框置灰；
- 表头、底部数据源、口径说明和 PNG 文件名（`风神考核看板_YYYYMMDD.png`）都用所选日期；
- 不写任何运单缓存（v3.9.0 起也不再读它做业务计算）。

### 加载速度

v3.8.0 时代历史日期要按终态时间整天分页拉运单（11-07 一整天 10529 单 ≈ 117 页 × 1.2s 节流，1–3 分钟）。v3.9.0 改成「排班 + 出勤明细」两个导出请求后，历史与今天都只要 **2–5 秒**。

### 刚过零点查 T-1 的特殊情况

出勤统计的时段明细通常次日才生成：11-08 00:21 导出 11-07 的明细只有表头、**0 行**。这种情况下 `detailToAttendance()` 会明确报「该日期的出勤统计明细尚未生成」，看板把**标二占比 / 考核得分显示「—」**，绝不把空表当成「无人达标」算成满屏 0 分。稍后重试或改查更早日期即可。

> 站点范围：导出接口要求 `teamIds`；页面用记住的 `wb_team_ids_v1`（0 请求），必要时回退旧运单缓存或查 1 页运单识别一次，详见上文「站点范围只识别一次」。实测 `teamIds: []` 会返回「没有该团队的数据权限」。

## 自动更新怎么工作

版本源是仓库根目录的 [`version.json`](./version.json)：

```json
{
  "version": "3.9.0",
  "notes": "本次更新说明",
  "download": "https://github.com/hubiqi/fengshen-ext/releases/download/v3.9.0/fengshen-ext-v3.9.0.zip",
  "published_at": "2026-11-08"
}
```

插件里的 `updater.js`（service worker）会：

| 时机 | 行为 |
| --- | --- |
| 安装 / 每次浏览器启动 / 每 6 小时 | 匿名读取 `version.json`（主源 `raw.githubusercontent.com`，超时/失败自动切 `api.github.com` contents API 备源，两个源都实时无缓存），与当前版本比较 |
| 发现新版本 | 工具栏图标出现红色 `NEW` 角标、风神页面悬浮球出现红标、看板顶部出现蓝色更新条（含版本说明） |
| 点「下载新版 zip」 | 直接下载 Release 里的安装包，并开始 30 分钟的快速磁盘轮询 |
| 新版文件覆盖到插件目录后 | 读到磁盘上的 `version.json` 比运行时新，自动 `chrome.runtime.reload()`，**无需手动去 `chrome://extensions` 点重新加载** |
| 看板「检查更新」按钮 | 随时手动触发一次检查；**无论结果如何都会在看板顶部显示一条反馈**：绿色「已是最新版本 vX · 已成功连接 GitHub（实际命中的域名），远端版本 vY · 检查时间」、蓝色「发现新版本 vX」或红色「检查更新失败：具体原因 · 无法确认是否有新版本（这不代表已是最新）」。不点按钮时也会显示上次检查的简版结论 |

**一个绕不开的限制**：Chrome 扩展运行在沙箱里，不能改写自己的安装目录。所以「检查 / 提示 / 下载 / 重载」全部自动，但**把新版文件放进插件目录**这一步需要你做一次：

1. 在看板更新条点「下载新版 zip」（或手动到 Releases 下载）。
2. 解压，把里面的文件**覆盖**到当初加载的那个插件目录（注意包含 `version.json`，不要套一层子目录）。
3. 完成。插件会在 1 分钟内自动检测并重载；也可以点更新条上的「已覆盖 · 立即生效」马上生效，或到 `chrome://extensions` 点「重新加载」。

> 如果你是通过 Chrome 应用商店安装的扩展，浏览器本身会自动更新，不需要本机制。本仓库面向「加载已解压的扩展程序」的使用方式。
> 仓库是公开的，检查更新**不需要任何令牌**；插件只读取版本号文件，业务数据只在你本机与风神站点之间流转，不会上传 GitHub。

## 发新版本（维护者）

```bash
# 1. 同步版本号、更新说明、下载 URL
node scripts/bump.mjs 3.9.1 "本次更新说明"

# 2. 提交并推送（网络不稳时用 HTTP/1.1 可避开 HTTP/2 Empty reply）
git add -A
git commit -m "release: v3.9.1"
git -c http.version=HTTP/1.1 push origin main
```

推送后 [`.github/workflows/release.yml`](./.github/workflows/release.yml) 会自动：

- 读取 `version.json` 的版本号；若该版本尚无 Release，则把运行时文件打成 `fengshen-ext-vX.Y.Z.zip`；
- 创建 `vX.Y.Z` Release 并附上 zip（版本未变化时重复推送不会重复发版，安全幂等）。

Release 出现后，所有已安装的插件最迟 6 小时内自动发现新版本；点「检查更新」可立即发现。

> 首次在某台机器上用 git 维护本地插件目录时，若本地目录原本不是 git 仓库，可执行：
> `git init && git remote add origin https://github.com/hubiqi/fengshen-ext.git && git fetch origin && git reset --hard origin/main`
> （该命令会用远端内容对齐本地，请先确认本地没有未提交的重要改动。）

## 常见问题

- **看板数字和系统对不上几十单**：v3.9.0 起完单量取自考勤统计，与运单「终态时间」口径存在 <1% 的正常差异（跨零点归日、改派结算）。若需要逐单核对，请用运单口径分支 `ASSESS.build(orders, …)` 复核。
- **换了账号 / 站点变了，看板报「未能识别站点范围」**：点工具条「重识站点」清掉记住的 `wb_team_ids_v1` 重新识别即可。
- **为什么以前经常全量同步**：旧版每 30 分钟无条件做一次全量校准，而自动刷新每 5 分钟一次，等于每半小时重拉当日全部运单；此外接口入库延迟导致「新增行数 === total 增量」不成立时也会降级全量。v3.4.3 已把定时全量换成滚动分片校准，并放宽对账（延迟单保留缓存、水位不推进、下次自动续补，连续 3 次补不齐才全量）。
- **提示的运单总数跟系统不一样 / 是不是把配送失败算进完单了**：没有算进去。看板「实际完单」只统计配送成功，配送失败单（接口 `state=90`）已剔除；进度条和底部统计里的「拉取 N 单」是接口返回的**全部运单**，本来就包含配送失败，所以比系统里的完单数大。v3.3.4 起进度条会直接写出「配送成功 M · 配送失败 F · 实际完单 M」，底部也有拆分。若对比表格里的「实际完单」仍与系统不同，请记下两个数字再排查（系统部分指标用的是「有效完成单」，还会剔除欺诈单，与考核看板口径不同）。
- **标2 人数为什么比系统少 / 改派单算不算完单**：v3.3.6 起骑手完单达标与标2 只算「非人工改派」的配送成功单（`isReassign != 1`），片区「实际完单」列仍含改派单，这是 KPI 第十三条「改派完单量在标1–标5 中剔除」的口径。看板底部会写明剔除单数、达标人数变化与跌破门槛的人数。注意当前接口无法识别「卡餐 / 兜底 / 养老餐改派单可计入完单」这三类例外，一律剔除。
- **怎么判断「没提示新版本」是真的已是最新，还是更新链接不通**：v3.3.3 起点「检查更新」必有结论。**绿色**＝已成功连上 GitHub，并写出命中的域名与远端版本号，此时确实没有新版；**红色**＝两个版本源都没打通，会列出每个源的具体错误，并明确写「这不代表已是最新」。此前版本的「已是最新」提示藏在本该隐藏的更新横幅里，看起来和链路不通完全一样，v3.3.3 已改为独立可见的反馈条。
- **提示「检查更新失败」**：v3.3.2 起主源 `raw.githubusercontent.com` 超时/失败会自动切 `api.github.com` 备源（每个源最多等 8 秒，备源用 `Accept: application/vnd.github.raw+json` 直接取原始 JSON，实时无缓存）；若两个源都被网络拦截，手动到 Releases 页面查看即可，不影响看板取数。
- **为什么不用 jsDelivr 等 CDN 镜像做备源**：它们对 `@main` 有长缓存，发版后仍返回上一版版本号，会让插件误判「没有新版本」。备源必须实时，因此选官方 API。
- **下载 404**：Release 由 GitHub Actions 在推送后自动生成，稍等 1–2 分钟再试；也可在 Releases 页面手动下载。
- **覆盖了文件但没自动重载**：确认 `version.json` 也一起覆盖、且目录就是 `chrome://extensions` 里显示的那个目录；点「已覆盖 · 立即生效」可强制检测。
- **数据看着不对 / 想强制校准**：点工具条「全量重拉」，忽略缓存重新拉当日全部运单并重建缓存。日常刷新仍走增量。
- **每次刷新还是显示「全量同步」**：v3.4.3 起已取消定时全量，正常刷新应稳定显示「增量同步」。若仍显示全量，底部「触发原因」会写明属于哪一类（跨天 / 换商 / 撤单 / 连续 3 次对账未补齐 / 缓存写入失败 / 手动全量重拉）。最常见的是「缓存写入失败」，通常是浏览器禁用了扩展本地存储。
- **时段怎么不全 / 排班里有「凌晨1」「早餐1」但看板没有**：v3.4.1 起时段矩阵按当日排班统计表动态生成，不再写死 7 个班次。11-05 / 11-06 这类排了早班的日期会显示 9 列，10-31 只有 7 列。看板底部会列出本次实际班次与来源；若显示「排班未取到故回退默认 7 班次」，说明排班导出失败，点「立即刷新」重试即可。落在未排班时段（如 02:00–06:00）的完单按约定不计入矩阵，但仍计入「实际完单」。
- **某时段完单量看着偏少**：先对照底部列出的班次清单与排班表。未排班时段的完单不会进矩阵；另外排班表里出现字典未收录的新班次名时，底部会点名提示「未识别班次」，需要把时间区间补进 `assess.js` 的 `PERIOD_DEFS`。
- **点「复制图片」没反应 / 提示生成图片失败**：先确认已安装 v3.4.0 及以上（`capture.js` 在插件目录里），必要时在 `chrome://extensions` 重新加载扩展。若提示「已自动下载 PNG」说明剪贴板被环境拒绝（页面失焦、企业策略、浏览器版本过旧），直接把下载的图片拖进钉钉即可；按住 Shift 点按钮可直接另存为文件。生成过程中按钮会显示「正在生成图片…」，完成后下方会写明是已复制还是已下载。
- **复制出来的图怎么和屏幕上不一样**：这是预期行为。导出固定按 1240px 桌面宽度、2 倍分辨率出图，不受浮层宽度和响应式排版影响，宽表不会换行；工具条、播报区、底部元信息也不属于看板画面，不会被截进去。字体与屏幕一致（见下条）。
- **「出勤达成」里的应排 / 实排 / 有效出勤分别是什么**：应排 = 排班统计「应排人数」，实排 = 排班统计「排班人数」，有效出勤 = 实时考勤里 `排班状态=排班` 且（时段有效在线时长 ≥ 该时段标准、时段完单量 ≥ 该时段标准）的去重骑手数，全天按 6h / 18 单。实排达成 = 有效出勤÷实排，应排达成 = 有效出勤÷应排（可能超过 100%，因为实排本就可能多于应排）。口径详见上面的「出勤达成」章节。
- **夜宵2 显示「统计中」，或全天数字和第二天看到的不一样**：考勤导出是当日实时快照，尚未结束的班次里多数骑手还没跑满时段标准，所以不显示 0% 告警，而是标「统计中 / 未开始」。想要定稿数字，直接在出勤页把日期切到 **T-1**：历史日期走时段明细，是次日定稿数据，不再显示「统计中」（实测 11-06 夜宵2 实时快照为 0 人，历史定稿 80 人）。
- **怎么在出勤页看昨天的达成 / 日期能选多早**：点工具条「T-1」或在日期选择器里挑日期，可回看最近 90 天（含今天）。切到历史日期后数据源标签变绿显示「历史明细」，自动刷新自动停用；「今天」按钮可一键切回实时快照。所选日期会写进表头、底部口径和 PNG 文件名。
- **想一天天往前翻日期，不想每次都开日历**：点日期框两侧的 ‹ / › 左右箭头，一次挪一天，连点可快速翻到任意历史日期；箭头切换和手工选日期走完全相同的校验与数据源。到今天时右箭头、到 90 天前时左箭头会置灰，悬停可看原因 —— 这是正常边界，不是按钮坏了。箭头属于工具条，不会出现在复制出来的 PNG 里。考核看板与出勤达成页都有这组箭头，但日期各自独立、互不联动。
- **怎么在考核看板看昨天的绩效 / 为什么 T-1 第一次要点几分钟**：点工具条「T-1」或日期框两侧箭头。T-1 的运单要按整天「终态时间」窗口全量分页（实测 11-07 有 10529 单 ≈ 117 页，页间 1.2s 节流），所以首次加载约 1–3 分钟，进度条会显示页数；切到别的日期再切回来会秒回。「立即刷新 / 全量重拉」会强制重拉该日。考核口径与今天完全一致，只是把运单、排班、考勤三条数据源都换成该日期的定稿数据。
- **选了 T-1 会不会把今天的增量缓存弄坏**：不会。`wb_orders_current` 是固定单键、只存当天，历史日期完全跳过读 / 写（进度条显示「历史定稿」），结果只放内存。切回「今天」时原来的终态水位与增量链路原样可用。
- **凌晨查 T-1 提示「该日期的出勤统计明细尚未生成」**：出勤统计的时段明细通常次日才生成，刚过零点导出会只有表头 0 行。此时看板把标二占比、考核得分显示「—」，不会把空表算成「无人达标」的 0 分。稍后再点「立即刷新」，或改查更早日期即可。
- **为什么历史日期的全天人数跟系统导出的「达成」列不一样**：系统「是否达成」标记在全天行不是按 6 小时 / 18 单算的（11-06 实测系统判 205 人，按运力标准应为 224 人，差 21 人）。本页完全忽略该列，只用明细里的有效在线时长与完单量手工判定，所以和系统标记不一致是**预期且正确**的。
- **历史日期提示「站点范围为空」**：`exportStatisticsDetail/1.0` 必须带 `teamIds`。先打开一次「考核看板」让它写入当日运单缓存，再回出勤页点「立即刷新」；缓存缺失时本页也会自动查一次运单首页补齐站点 ID。
- **复制出来的图太长 / 不想把出勤达成放进图里**：v3.6.0 起两个入口已经完全分开，原考核看板的 PNG 永远不含出勤达成表，不需要任何开关；出勤页的「复制图片」也只截自己的两张达成表。
- **出勤达成显示「暂不可用」**：说明排班统计或考勤缺关键列（例如旧导出没有 `排班人数`、`排班状态`、`时段完单量`）；历史日期还要求明细里有 `骑手ID / 时段 / 有效在线时长 / 完单量 / 站点名称 / 是否排班`。页面会点名列出缺什么，且不会把空表塞进 PNG。缺「完单量」时会自动降级为只看有效在线时长并标注。
- **字体不好看 / 字太小发虚**：v3.4.2 起统一用系统默认 UI 字体栈（macOS = SF Pro + 苹方，Windows = Segoe UI + 微软雅黑），表格数字启用等宽对齐，中文、西文、数字字形更协调；同时移除了 v3.4.1 在班次变多时给整张表加的 `compact` 小字号（表头最小 10px）。现在无论 7 / 9 / 11 个班次，一级表头 13px、二级表头与完单率 12px、正文 13px 都固定不变，只压缩列宽。`capture.js` 的导出根节点用同一份字体栈，保证 PNG 与屏幕观感一致。
- **权限说明**：`alarms`（定时检查）、`downloads`（下载 zip / PNG）、`clipboardWrite`（复制图片，MV3 无安装警告）、`https://raw.githubusercontent.com/*` 与 `https://api.github.com/*`（主/备版本源）均为自动更新与复制图片所需；`storage` / `unlimitedStorage` 为运单增量缓存所需（数据只存本机，不上传）；`tabs` / `scripting` / `declarativeNetRequestWithHostAccess` 为原有看板取数能力。
