# 风神考核看板（Chrome 扩展 · 通用版）

风神页面常驻**一颗「看板」总按钮**：点开是一个小菜单，里面有三个互不干扰的功能入口 —— 「**考核看板**」（规划单量完成率、标 2 骑手占比、考核得分、时段 × 商圈片达成矩阵）、「**出勤达成**」（应排 / 实排 / 有效出勤、实排达成 / 应排达成）与「**运力模块**」（骑手账单 × 人资在职 × 三方人资 × 本月出勤 × 异常订单，一行一条账单的 22 列明细）。三个入口各打开一个独立页面、各导一张图；功能分开，但入口收拢到同一个按钮里，页面上不再散落多颗悬浮球。全部数据在本机浏览器内获取，跟随当前浏览器登录态，换账号自动换商，无需本地服务、无需 Python。

## 安装

1. 到 [Releases](https://github.com/hubiqi/fengshen-ext/releases/latest) 下载最新的 `fengshen-ext-vX.Y.Z.zip`，解压到一个**固定、不会移动**的目录（例如 `~/Extensions/fengshen-ext`）。
2. 打开 `chrome://extensions`，右上角开启「开发者模式」。
3. 点「加载已解压的扩展程序」，选择刚才解压的目录。

> 环境要求：Chrome / Edge **111 及以上**（service worker 使用 ES module 与 Promise 风格扩展 API）。
> 已在风神页面登录的前提下，点击页面右侧的「看板」总按钮，在菜单里选「考核看板」「出勤达成」或「运力模块」；也可点浏览器工具栏图标直接展开/收起面板。

## 运力模块（v3.15.0 建页 / v3.16.0 增补 6 列 / v3.16.1 跨站复合键）

第三个独立入口。把五个互不相关的页面拼成**一行一条账单**的明细表，用来核对薪资账单、人员在职状态、三方人资来源，以及本月的出勤与异常订单情况。所有取数都在浏览器内完成，跟随当前登录态，不依赖本地服务。

### 五个数据源与接口

| 数据源 | 页面 | 接口 | 提供字段 |
| --- | --- | --- | --- |
| 骑手账单管家 → 账单查询 | `?targetId=58484#/salary-bill-ub` | `POST xtop.lpd.price.mng.zsSalaryBillQueryFs.pageQuerySalaryBill/1.0`（`bizType=3`、`billCycle=YYYY-MM`、`pageSize=500`，按 `total` 翻页） | 账单ID、站点id/站点、骑手id/姓名、基础薪资方案名称、排班内/外单量、一口价单量明细（取分离 / 送分离）、账单总金额、预支、住宿费用、车辆租金 |
| 人资综合服务 → 成员管理（**全部**状态） | `?targetId=61068#/humanResource/staffManagement/index` | `GET app2-edu.ele.me/kunkka-svr/ehr/staff/knight/list?pageIndex=N&pageSize=500`（**不带 `workStatus`**，含在职与离职） | 是否在职（`workStatus` 1 在职 / 2 离职）、入职时间、离职时间 |
| 招募缺口管理 → 线索结果明细 | `?targetId=61364#/index?tab=station` | `POST xtop.knight.task.mng.growth.knightRecruitResultRead.queryAgencyKnightRecruitResult/1.0` | 是否三方人资：命中带 `headHunterCompanyName` 的线索即为「是」，公司名可悬停查看 |
| 出勤统计 → 导出明细数据（**本月**） | 与出勤达成同源 | `POST xtop.fs.special.examine.exportStatisticsDetail/1.0`（`teamIds` + `startDate/endDate`，**单次最多 7 天**，返回 OSS xlsx 链接） | 本月班次异常数（除全天）、首跑时间 |
| KPI管理 → 考核数据明细 · UB考核运单明细 | `?targetId=56740#/kpi/detail` | `POST xtop.performance.fs.opp.perfDetail.queryDetailList/1.0`，`tabCode=TRACK_UB`，4 个 Radio 筛选各查一次（`pageSize=100`） | 物流责 / 投诉 / 差评 / 提前点 |

前三源**并行**取数先出主表，后两源在主表出图后**异步补齐**：任一组失败只让对应列显示「—」，不阻断出表；切月会丢弃过期结果。出勤明细按 7 天分段导出 xlsx，月份切换时整段重取（当月取到今天）；`teamIds` 直接复用当月账单里的站点 id，不额外发请求。直接请求失败时自动切「静默桥接」（`BRIDGE_GET` 支持 GET 型接口、`FETCH_BINARY` 兜底下载 xlsx）。

> **考核运单明细只拉「有问题的订单」**：整月全量运单约 24 万条，插件**绝不发起不带筛选的全量查询**，只按 4 个筛选条件各查一次（每类最多 10 页 / 100 单），按运单ID 去重后按「骑手 id ＋ 站点 id」汇总，实测一个月只有约 30 条问题订单。
> 「提前点送达不满意单」没有独立筛选项，但 3 个 `is_early_delivery_*` 子筛选（投诉 / 差评 / 索赔）的并集完整覆盖该列（10 月实测并集 17 单全部命中，日指标汇总 16 单）。

### 跨站骑手按「骑手 id ＋ 站点 id」归集（v3.16.1）

一个骑手可能在多个站点各有一条账单（例如 A 站全职 + B 站兼职），主表因此会有多行。**本月班次异常数 / 首跑时间 / 物流责 / 投诉 / 差评 / 提前点这 6 列全部按复合键 `骑手id \u0001 站点id` 归集，跨站骑手各站分开计**，A 站的问题订单只落在 A 站那一行，不会重复记到 B 站。

- 出勤明细 xlsx 读「站点ID」列，考核运单明细读「站点ID」列；两者与账单 `teamId` 是同一套 id（实测 7 个站点全部命中）。
- 按运单ID 去重、按复合键累加；账单行用自身 `teamId` 精确查表。
- 若某个数据源偶尔缺「站点ID」列，数据归到通配键，**只有该骑手在账单里仅出现一个站点时**才兜底采用，避免把无站点信息的数据摊到跨站骑手的某一行。
- 表格下方说明会提示当月有多少名跨站骑手；CSV 里同样带「站点id」列，可直接按两列透视核对。

## 完单直接取自考勤统计（v3.9.0）

「骑手根本不需要同步运单」——出勤统计本来就是 **骑手 × 时段** 粒度，每行同时带着「有效在线时长」和「完单量」，全天行再给出全天合计。所以考核看板的完单量现在直接从这里读，不再分页拉运单。

| 指标 | v3.8.0 及之前 | v3.9.0 起 |
| --- | --- | --- |
| 实际完单 / 时段完单 / 骑手完单 | `queryTracking/2.0` 分页拉运单，逐单判 `stateDesc` 是否「配送成功」 | 出勤统计的「全天」行 / 时段行的 **完单量** |
| 每次刷新请求数 | 几十～上百页（90 条/页 + 1.2s 节流），历史日期 1–3 分钟 | **2 个导出请求**，通常 2–5 秒 |
| 本地缓存 | `wb_orders_current` 存当日运单，跨天/换商失效 | 不再写运单缓存，只记一份 `teamIds` |
| 口径一致性 | 自己按状态位判成功单 | 与考核系统同一个数据源 |

### 为什么口径能对上

用 2026-11-06 真实数据逐单对账：整天运单 **9345 单**，其中「配送成功」**9051 单**；出勤统计的全天完单合计**也是 9051 单**，而且**逐骑手 233/233 完全相等，偏差 0**。也就是说：

> 出勤统计的「全天完单量」= 运单里 `state=40 配送成功` 的单数，一分不差。它本身就是考核系统的结算口径。

原先以为的「0.7% 差异」只是把运单总数（含配送失败）跟完单数混在一起比了；按成功单比，两边完全一致。这也直接说明了一件事：**出勤统计没有剔除人工改派**，这正是 v3.10.0 要补的（见下一节）。

> 同一天同一套排班，v3.10.0 算出的规划单量 9386、实际完单 9051、完成率 96.4%、完单达标 206、标2 206、应排 231、标二占比 89.2%、考核得分 85.2；出勤达成的 231 / 232 / 224 与改造前完全一致。

### 站点范围只识别一次

导出接口传 `teamIds: []` 会返回「没有该团队的数据权限」，所以必须带站点 ID。取法按代价从低到高：

1. `localStorage` 里记住的 `wb_team_ids_v1`（**0 请求**，日常刷新都走这条，两个页面共用）；
2. 旧版留下的运单缓存（**0 请求**，只读 `teamId`，用于从 v3.8 平滑迁移）；
3. 实在没有才查 **1 页运单**（1 请求，只为拿 `teamId`）。

换账号 / 站点增减后站点范围会变，点工具条的「**重识站点**」清掉缓存重拉即可。

### 标2 口径：只查改派单，把剔除补回来（v3.10.0）

v3.9.0 为了省掉运单同步，顺手把「人工改派剔除」也丢了 —— 当时以为出勤统计已经按结算规则统好，实测发现并没有（见上一节：9051 = 9051，一分没剔）。KPI 第十三条要求**改派完单量在标 1–标 5 中剔除**，所以这一步必须补。

关键在于：不用为了拿改派单去拉全量运单 —— `queryTracking/2.0` 支持 `isReassign` 直接筛选。

```js
// dashboard.js
buildQueryPayload(page, undefined, undefined, date, { isReassign: 1, teamIds })
```

实测 11-06 全天 9345 单里，改派单只有 **159 张**（2 页就取完），其中配送成功 **149 张**。于是整商的取数变成：

| 请求 | 次数 | 用途 |
| --- | --- | --- |
| `exportSchedule/1.0` | 1 | 规划单量 / 应排人数 / 时段预估 |
| `exportAttendance` 或 `exportStatisticsDetail` | 1 | 完单量 + 有效在线时长 |
| `queryTracking/2.0`（`isReassign=1`） | 2～4 | **只拿改派单名单**，用于剔除 |
| `queryTracking/2.0`（无条件） | 0～1 | 仅首次识别 `teamId`，之后走缓存 |

仍然是秒级，没有回到「上百页运单」。

处理细节：

- **只剔「配送成功」的改派单**。改派了但最终取消 / 失败的单本来就不算完单，再扣一次就多扣了（11-06：159 张里 10 张未送达，不参与剔除）。
- **只动骑手达标口径**。片区「实际完单」、订单完成率、时段完单仍是考勤原值（含改派单），与 KPI「只剔除标 1–标 5」一致。
- **扣减后钳到 0**，不会出现负数达标。
- **`null` 与 `[]` 严格区分**：`reassignOrders` 是 `null` = 改派查询失败，此时**不剔除**并在底部写明「本次未取到改派单」，宁可显示偏高的人数也不静默少扣；`[]` = 查过了、当天确实没有改派。

> 11-06 实际影响：完单达标 208 → **206**，标2 208 → **206**，2 人因改派单跌破门槛。
>
> ⚠️ 标二占比跟着从 **90.04% 掉到 89.18%**，而考核得分对标二占比是**台阶函数**（≥90% 满分 100，80–90% 线性 80–90 分），跨过 90% 这条线后得分从 **91.7 → 85.2**。这不是算错了，是剔除改派后本来就该有的结果 —— 之前的高分是被改派单抬上去的。

如果哪天真要完整复核，`ASSESS.build(orders, sch, att, date, XLSX)` 仍保留**全量运单口径**（传非空 `orders` 即生效），与「考勤 + 改派单」应当得到同一组人数。

### `sync.js` 还在，但只做迁移

运单增量同步（终态时间水位、滚动分片校准、对账续补）的代码原样保留在 `sync.js` 里 —— 两个页面仍会用它**只读**旧缓存里的 `teamId`（0 请求完成站点范围迁移），除此之外不再调用。看板进度条也不会再出现「增量 / 全量 / 水位」之类的字样。

### 运单口径：拉取总数 ≠ 实际完单（历史说明）

v3.8.0 及之前看板按运单统计完单时，`queryTracking/2.0` 的 `total` 是**当日全部运单**，包含「配送失败」单（实测 `state=40 / 配送成功`、`state=90 / 配送失败`，某日首页 90 单里就有 2 单失败）。旧版会在进度条里把「拉取 N 单（配送成功 x · 配送失败 y）」与「实际完单」分开标注，避免把失败单误看成完单。v3.9.0 起完单改由出勤统计给出，这套拆分文案不再出现；保留此段是因为：万一你通过 `ASSESS.build(orders, …)` 走运单口径复核，规则仍然是**只算配送成功、失败单从不计入**。

### 标2 骑手口径：剔除人工改派完单（v3.3.6）

KPI 第十三条「人工改派结算限制」：**改派完单量在标 1–标 5 中剔除** —— 系统已指派骑手后，站长手动把订单改派给新骑手，这类完成单不计入该骑手的运力达标标准。

`queryTracking/2.0` 每条运单带 `isReassign` 字段（`0` / `1`，实测某日首页 90 单里有 3 单为 `1`，且都是配送成功单）。v3.3.6 起 [`assess.js`](./assess.js) 的处理：

| 指标 | 口径 |
| --- | --- |
| **完单达标人数 / 标2 骑手数** | 只累计「配送成功 **且** `isReassign != 1`」的单；门槛仍是 UB≥26 / 其他≥24，标2 另需全天有效在线时长≥6h |
| **片区实际完单 / 订单完成率 / 时段完单** | **不变**，仍按全部配送成功单统计 —— KPI 只规定标1–标5 剔除，规划单量完成率不在此列 |
| 判定兼容性 | 同时兼容 `isManualReassign` / `reassignFlag` 等可能的字段名；字段缺失、为 `0`、为「否」一律按未改派，宁可少剔除也不误判达标骑手 |

看板底部会写出本次剔除量与影响，便于对账，例如：

```
标2口径：人工改派成功单 3 单已从骑手达标统计剔除（完单达标 128→126、标2 96→95，2 人因此跌破门槛）；片区实际完单仍含改派单
```

> **已知限制**：KPI 条款还规定「卡餐单、兜底单、养老餐改派单可计入完单」，但这三类例外需要出餐时间 / 兜底标记 / 业务品类等额外数据，当前运单接口只有 `isReassign` 一个布尔位，无法区分人工改派与这些例外，因此 v3.3.6 **对所有改派成功单一律剔除**。若结算需要对例外单放行，需另外接入能识别例外类型的数据源，再在 `isReassigned()` 里加白名单。

## 一键复制图片（v3.4.0）

看板工具条的「**复制图片**」按钮会把 `#sheet`（即 1:1 复刻钉钉考核看板的那块画面）渲染成一张 **1240px 宽、2 倍像素密度的 PNG**，写进系统剪贴板，随后可直接 `Ctrl/⌘+V` 粘贴到钉钉 / 微信 / 文档里。

- **只截看板画面**：不含工具条、更新提示、进度条、播报区和底部元信息；与原先「纯净看板 + 系统截图」看到的内容一致。
- **固定桌面版排版**：导出时忽略响应式 `@media` 规则，固定按 1240px 逻辑宽度出图。即使看板浮层很窄、屏幕上是「手机排版」，复制出来的图仍是钉钉下发的那张宽表，不会换行或截断。
- **纯本地、零依赖**：[`capture.js`](./capture.js) 用 `SVG foreignObject + Canvas` 实现，不引入 html2canvas / dom-to-image 之类的第三方库，不发起任何网络请求，业务数据不出浏览器。
- **失败自动降级**：剪贴板不可写（权限策略、浏览器版本、页面失焦等）时，自动下载同名 PNG 文件，仍可拖进钉钉 / 微信；按钮下方会明确写出实际结果（已复制 / 已另存 / 已自动下载）和图片尺寸。
- **按住 Shift 点击**：直接另存为 `风神考核看板_YYYYMMDD.png`，适合归档或需要原图的场景。
- **两个入口各导各的图（v3.6.0）**：原考核看板只截 `#sheet` 的考核画面；独立出勤页只截自己的两张达成表，另存为 `风神出勤达成_YYYYMMDD.png`，不会把新表混进原来的看板图。
- **文件名跟所选日期走（v3.7.0）**：出勤页选了 T-1 或更早日期，PNG 文件名与画面里的日期都用所选日期，不会误写成今天。

实现上，`ClipboardItem` 里放的是 `Promise<Blob>`，因此 `navigator.clipboard.write()` 在点击的同一个任务内就发起，PNG 渲染再慢也不会丢掉 Chrome 要求的 transient user activation。manifest 额外声明了 `clipboardWrite`（MV3 有效、无安装警告），看板 iframe 也显式带 `allow="clipboard-write *"`，两者共同保证在风神页面浮层里同样能复制成功。

## 时段矩阵按排班动态生成（v3.4.1）

旧版在 `assess.js` 里**硬编码了 7 个工作班次**（早餐2 / 午高峰 / 下午茶1 / 下午茶2 / 晚高峰 / 夜宵1 / 夜宵2），但排班表里的班次数是按天、按合作商变化的。实测 `data/raw/` 的真实排班统计表：

| 排班文件 | 「时段」列取值 | 工作班次 |
| --- | --- | --- |
| `排班数据_20261031.xlsx` | 休息、早餐2、午高峰、下午茶1、下午茶2、晚高峰、夜宵1、夜宵2、全天 | 7 个 |
| `排班数据_20261105.xlsx` / `1106` | 上面 **+ 凌晨1 + 早餐1** | **9 个** |

旧版第 `PERIOD_NAMES.includes(per)` 这一句会把「凌晨1」「早餐1」直接丢掉：这两列的**预估单量不进矩阵**，00:00–08:00 的完单也因为 `periodOf()` 只认 7 个时间片而全部不计入时段矩阵 —— 这就是「时段不全」。

v3.4.1 的处理：

1. **先解析排班，再定口径**：`ASSESS.build()` 内对排班统计表做两遍扫描 —— 第 1 遍只读当天出现过的班次名（排除「全天」「休息」），第 2 遍才按这批班次累加规划单量 / 应排人数 / 时段预估单量。时段矩阵的列、运单时间归类、合计行全部共用这一份 `periods`。
2. **班次时间区间来自 KPI 标准**：排班表只有班次名、没有时间范围，运单接口也只有 `completeAt` / `trackingFinishAt` 时间戳。因此 `assess.js` 内置了与 `config.py` 的 `PERIOD_STANDARDS` 逐行对齐的 **11 时段字典**（凌晨1 00:00-02:00、凌晨2 02:00-04:00、凌晨3 04:00-06:00、早餐1 06:00-08:00、早餐2 08:00-10:30、午高峰 10:30-13:30、下午茶1 13:30-15:30、下午茶2 15:30-17:30、晚高峰 17:30-20:00、夜宵1 20:00-22:00、夜宵2 22:00-24:00），按时间先后输出当天排班里出现的班次。
3. **未排班时段的完单**：只计入「实际完单」和完成率，**不进时段矩阵**，矩阵与排班严格一一对应。例如 11-06 排了「凌晨1」但没排「凌晨2 / 凌晨3」，则 02:00–06:00 的完单不会出现在任何时段列。
4. **排班取不到时兜底**：回退到旧版的 7 个默认班次，看板底部会写明「排班未取到故回退默认 7 班次」，不会静默用错口径。
5. **表格宽度**：表 2 总宽固定 1218px，班次变多时**压缩子列宽**（7 班次 72px、9 班次 56px、11 班次 45px），而不是把表格撑到 1506px —— 这样「复制图片」的 1240px 画布不会被裁切。v3.4.2 起字号不随列宽缩小：一级表头是 `colspan=2`（最窄也有 90px），完全放得下 4 字班次名，正文与二级表头始终保持常规字号。

看板底部会列出本次时段口径，例如：

```
时段矩阵：按当日排班 9 个班次动态生成（凌晨1 / 早餐1 / 早餐2 / 午高峰 / 下午茶1 / 下午茶2 / 晚高峰 / 夜宵1 / 夜宵2）；落在未排班时段的完单不计入矩阵，但仍计入实际完单
```

> **为什么没有真的把排班请求挪到运单之前**：`exportSchedule/1.0` 的 `teamIds` 是从运单明细里收集的站点 ID，强行提前且传空数组可能拿不到全量排班。而 `ASSESS.build(orders, schSheets, attSheets, …)` 本来就是一次性拿到三份数据再计算，所以「先知道有哪些班次」在 `build()` 内先解析排班即可实现，效果相同且不破坏取数依赖。
>
> **未识别班次**：若排班出现了字典里没有的新班次名，它无法做时间归类，不会进矩阵，但预估单量仍计入「规划单量」；看板底部会点名提示，需要把新班次补进 `PERIOD_DEFS`。

## 出勤达成：应排 / 实排 / 有效出勤（v3.5.0，v3.6.0 起独立入口，v3.7.0 起可选日期）

「出勤」入口打开的是一张独立的看板，含两块「商圈片 × 时段」达成矩阵（v3.12.0 起收成一组页签，一次看一张）：**上方百分比 + 下方「有效出勤/分母」**，配色为 ≥100% 绿、80–99.9% 橙、<80% 红。

| 指标 | 数据来源 | 口径 |
| --- | --- | --- |
| 应排 | 排班统计 `应排人数` | 按站点→商圈片、按当天时段求和；「全天」取排班统计的全天行 |
| 实排 | 排班统计 `排班人数` | 同上，即实际排上班的人数 |
| 有效出勤 | 实时考勤（今天）/ 出勤统计时段明细（历史日期） | `排班状态=排班` 且（**时段有效在线时长 ≥ 该时段标准** 且 **时段完单量 ≥ 该时段标准**）的去重骑手数；全天按 6h / 18 单 |
| 实排达成 | 有效出勤 ÷ 实排 | ≤100%（有效出勤是实排的子集） |
| 应排达成 | 有效出勤 ÷ 应排 | 可 >100%（多排班不设上限），例如凌晨1 `4/1 = 400%` |

时段标准与 `config.py` 的 `PERIOD_STANDARDS`（KPI PDF 第 9-10 页）逐项对齐：凌晨1 90 分钟/1 单、早餐1 90/1、早餐2 120/1、午高峰 150/5、下午茶1 90/2、下午茶2 90/2、晚高峰 120/3、夜宵1 90/2、夜宵2 90/2；「全天」按运力标准 1 等效的 **6 小时 / 18 单**。列同样按当天排班实际班次动态生成（全天 + 7/9/11 班次），总宽锁 1218px，字号保持常规，不撑破「复制图片」的画布。

- 顶部三数概览直接给出整商全天的 **应排 / 实排 / 有效出勤** 与两个达成率；鼠标悬停任意格子会显示该格三个数。
- **今天的考勤是实时快照**：还没结束的班次若暂时无人达标，显示「统计中 / 未开始」而不是误报 0%，当晚继续刷新或次日查看会自然补齐；**历史日期是定稿数据，不再显示「统计中」**。
- 独立页面自带「日期 / 今天 / T-1 / 立即刷新 / 复制图片 / 通道 / 纯净看板 / 考核看板 ↗」；5 分钟自动刷新只对「今天」生效，历史日期不重复拉取；**不拉运单明细、不写运单缓存**，站点 ID 优先复用原看板已落盘的运单缓存（0 次额外请求），缓存不存在时只查运单第 1 页（1 次请求）。
- 排班统计或考勤任一侧缺关键列时，页面会点名提示并**不渲染两张空表**，不会把空表塞进 PNG；若考勤导出缺「完单量」列，则降级为只看有效在线时长并明确标注。
- **日期选择的完整口径见下一节**。

> 口径已用 2026-11-06 真实排班 / 考勤 xlsx 与两张截图逐格对账：应排、实排共 60 个分母完全一致，白天 40 个有效出勤分子完全一致；截图里的「全天」「夜宵2」分子来自当天结束后的完整快照，本地 22:10 导出的考勤快照会略小，属预期差异。

### 点单元格看炸班明细（v3.11.0）

「炸班」= 当天排了班（`排班状态 = 排班`），但当班次没达到有效出勤标准的骑手。他们既算不进「有效出勤」，又占着「实排」名额，是达成率掉下来的直接原因 —— 所以要看得到是谁。

- 点实排达成 / 应排达成表里的**任一格子**（团队 × 时段，含「全天」列），弹出该班次的炸班骑手清单：**姓名（附骑手 id）/ 站点 / 有效在线 / 完单 / 未达标原因**。
- 原因分四类：`未出勤`（有效在线与完单都是 0）、`时长·完单均不足`、`有效在线不足`、`完单不足`；清单按有效在线升序，最差的排最前，未出勤用浅红底标出。
- 弹窗副标题直接给该格的 **应排 / 实排 / 有效出勤 / 实排达成** 与该班次的判定标准（例如「有效在线 ≥1 小时 30 分 且 完单 ≥2 单」）。
- 两者关系恒成立：**有效出勤 + 炸班 ≈ 实排**（两套表口径允许 ±2 人）。11-06 对账：实排 232、有效出勤 224、全天炸班 8 人；全商炸班 27 人次 / 13 个格子，逐人（姓名、有效在线、完单）与原始明细完全一致。
- 关窗支持右上角 ×、点遮罩、Esc 三种；**Esc 先关弹窗**，不会把整个看板面板一起关掉。
- 弹窗挂在 `#sheet` 之外，**「复制图片」永远只导两张表，不会把弹窗截进去**；单元格只加 hover 底色与手型光标，静态版式、导出图与之前完全一致。
- 查历史日期时清单是定稿的；查今天（实时快照）时，未结束班次里「还没跑满」的骑手也会列出 —— 弹窗顶部会明确提示「该班次尚未结束，可能还在补齐」，别当定论。
- 明细口径以考勤表「排班状态 = 排班」为准，与排班统计的「排班人数」来自两张不同的表，人数可能差 1–2 人，弹窗里也写明了这一点。

### 实排 / 应排 页签切换（v3.12.0）

两张表的分子是同一份「有效出勤」，只有分母不同（实排 = 排班人数，应排 = 应排人数），并排竖着放等于把几乎一样的数字滚两遍。v3.12.0 把标题下方改成一组页签，**一次只看一张表**：

- 标题下方是「**实排达成 ｜ 应排达成**」两个页签，默认看实排达成；点另一个换分母，表格内容与配色随之切换。
- 切换**只改显示**：不重新取数、不重算口径，两张表在切换前都已渲染好，点了即刻生效（取数与切页签互不影响）。
- 选择记在本机（`localStorage` 的 `wb_att_view`），下次打开出勤页还是上次看的那张；页签也可以用键盘 ← → 切换。
- 页签在 `#sheet` 内，**「复制图片」导出的 PNG 也能看出当前看的是哪个口径**；表标题里的分子分母与页签一致，贴到群里不会看错。
- 概览区仍同时给出两个达成率（`实排达成 / 应排达成`），只有矩阵收成一张 —— 想看另一个分母点一下即可，不用再截两张图。
- 「炸班明细」在两张表里都能点开，格子与口径不受页签影响。

### 炸班明细矩阵：一人一行 × 时段列（v3.14.0）

> v3.13.0 曾把清单做成「按班次分行」（每班次一条横幅 + 下面挂人）；v3.14.0 起改成下面这种**一人一行的横向矩阵**，一眼能看完某个骑手一整天哪些班达标、哪些班炸了，还能连着看前几天的趋势和 T+1 的排班。

```
站点            姓名+id             异常次数  凌晨1 早餐1 早餐2 午高峰 下午茶1 下午茶2 晚高峰  T-3 T-2 T-1  T+1排班
福清市凤凰站-UB   李辉辉 / 1139840042     1      ✓                 ✗                      0   0   0   凌晨1、晚高峰、夜宵1、夜宵2
福清市福清万达站-UB 黄伟勋 / 1164900072    1      ✓                              ✗        0   0   0   午高峰、下午茶1、下午茶2、晚高峰
```

- **一人一行**：只列当天至少有一个班次炸班（`✗`）的骑手；一个骑手在多个班次出问题，也只占一行。
- **时段列三态**：绿 `✓` 该班次达标、红 `✗` 炸班、空白 = 没排这个班。`✗` 直接取 `attendance.fails`（与点格子弹出的明细同源），`✓` 取考勤原始表里「排班状态 = 排班」且不在 fails 的格子——不重算判定标准，口径不会和上方达成矩阵漂移。
- **列按当日排班动态生成**：凌晨1 / 早餐1 / … / 夜宵2 有几列取决于当天实际排了哪些班；**列宽按内容自适应**（不再写死 `colgroup`），站点、姓名、「T+1排班」都完整换行显示、不省略；T0 还会去掉没跑完的班次。
- **异常次数 = 这一行 `✗` 的个数**：打开「全天」开关或班次跑完后自动累加，永远和表格里看到的勾叉对得上；按异常次数降序排，最差的在最前。
- **T-3 / T-2 / T-1**：大前天 / 前天 / 昨日各自的「炸班班次数」汇总（按所选日期相对计算）。每天异步发 1 次 `exportStatisticsDetail/1.0`，用与当天相同的时段标准手工判定、按骑手汇总；结果按日期缓存在内存，切日期不重复拉，取不到显示 `—`。**主表不等它**：先出图，三天数据回来再一次性补进格子。
- **T+1排班**（v3.16.2 起由「明日排班明细」改名）：**T = 当前所选日期**，这一列是该骑手在 **T 的次日（T+1）** 排了哪些时段；查历史日期时显示的是「该日 + 1 天」的排班，**不是真实的明天** —— 避免选了以前的日期时误以为列的是今天之后的明天。表头 hover 与页面口径说明都写明了这一点。`exportSchedule/1.0` 的 `endDate` 本来就含次日，返回的 xlsx 里 `排班表(行)`（或宽表的次日日期列）已带每人排班，**0 额外请求**；`休息` 与查无数据分别显示为「休息」「—」。
- 矩阵是**两张表共用**的附录，切「实排 / 应排」页签不影响它；数据缺失时整块隐藏，不会把空表塞进导出图。

#### 列宽自适应、T+1排班标红与近三天追溯（v3.14.0）

- **宽度自适应**：矩阵不再写死 `colgroup` 的固定像素列宽，改用 `table-layout: auto` 让浏览器按内容分列；「T+1排班」拆成一个个班次小块，整段自动换行，宁可把行撑高也绝不截断。标题、口径说明与表格同为 100% 宽。导出图的画布默认仍是 1240px 逻辑宽（2 倍图 2480px），但会先量一遍 `#sheet` 里各块的实际宽度，**内容更宽时自动放宽画布**，右侧列不会被裁掉；常规画面导出的尺寸不变。
- **标红命中本日炸班**：T+1排班里，凡是与该骑手**本日炸班班次**同名的班次都标红（红字 + 浅红底）。例如今天「午高峰」炸了、T+1 又排了午高峰，这一块就是红的；纯文本班次保持灰色。红色班次带 `role="button"` / `tabindex`，鼠标与键盘（Enter / 空格）都能点开。
- **点击追溯**：点红色班次弹出「近三天班次异常追溯」，按 **日期 / 是否达标 / 有效时长 / 有效完单** 四列，逐日列出大前天（T-3）、前天（T-2）、昨日（T-1）该骑手在**同一个班次**的判定记录；达标显示绿 ✓、未达标显示红 ✗ 并给浅红底。口径与当天完全一致：`有效时长 ≥ timeMin` 且 `有效完单 ≥ orders`，任一不足即炸班。
  - 数据来自前面那 3 次历史出勤明细请求，按日期缓存在内存中，点开时 **0 额外请求**；某天没排这个班或明细尚未生成，该行显示「未排该班 / 无明细」，取数中显示「取数中…」。
  - 弹窗与「炸班明细」弹窗一样放在 `#sheet` 之外，**不会进「复制图片」**；支持 × / 遮罩 / Esc 关闭，打开时来源行高亮。
- 追溯弹窗的四列正是排查「连着几天都在这个班上炸」所需的三要素：哪天、达没达标、差在时长还是完单。

#### T0 只显示已结束的班次

今天查实时快照时，**还没跑完的班次不进表也不算炸班**——人还在陆续上线、单还在攒，这个时点判定「不达标」既不公平也没意义（11-06 晚 20 点看快照，夜宵2 有 84 人才刚上线 10 分钟、0 单，全被算成炸班）。

| 场景 | 达成矩阵列 | 炸班明细矩阵的时段列 |
| --- | --- | --- |
| 今天（T0） | 全天 + **已结束**的班次 | 只列已结束班次，**默认不含「全天」** |
| T-1 及更早 | 全天 + 全部班次（定稿） | 全部班次，含「全天」列 |

- 判定「已结束」用班次时间窗：`当前时间 ≥ 该班次 end`，全天列在达成矩阵里始终保留。
- 页面口径说明会点名「今天只显示已结束的班次」，底部元信息还会写「…（夜宵1、夜宵2 进行中）」并在炸班班次后注明「另有 N 人次暂不计入：全天 … + 未结束班次 …」。
- 班次一结束，下次刷新（5 分钟自动刷新）就会自动出现，不需要手动切日期。

#### T0 的「全天」列默认关闭（v3.13.1 起）

「还没结束不准」——班次可以等它跑完，但**全天永远要等到这一天过完**才准。今天 20 点按「有效在线 ≥6 小时 且 完单 ≥18 单」去判「全天未达标」，把还在路上、单还在攒的人列成炸班，是假阳性。

| | 今天（T0） | T-1 及更早 |
| --- | --- | --- |
| 炸班明细的「全天」列 | **默认不显示** | 照常显示（定稿数据） |
| 达成矩阵表头的「全天」列 | 保留，不变 | 保留 |
| 顶部「整商全天」概览 | 保留，不变 | 保留 |
| 清单标题右侧开关 | 显示，默认关 | 隐藏（不需要） |

- **开关**：标题右侧 `☐ 显示全天（未结束，不准）`，点一下变琥珀色勾选态，全天列立刻出现；再点一下关掉。切换**只重画清单，不重新取数**，选择写在 `localStorage.wb_att_roster_day`，刷新后沿用。
- 用按钮 + `role="switch"` / `aria-checked` + CSS class 表达状态，而不是原生 checkbox：`foreignObject` 克隆生成导出 PNG 时表单控件的勾选态容易丢。
- 关掉时标题补 `· 不含全天`、说明点明判定不准；打开时说明标注「全天列为手动打开，仅供参考」，底部「暂不计入」同步减掉这部分。

## 选择日期：T-1 与历史时段明细（v3.7.0）

| T-1 及更早 | `exportSchedule/1.0`（支持历史日期） | `exportStatisticsDetail/1.0`（出勤统计 → 导出明细数据） | 关闭（定稿数据） |

**左右箭头逐日快切（v3.7.1）**：日期框两侧各有一颗 ‹ / › 箭头，点一次往前 / 往后挪一天，比打开日历挑日期快得多。切换复用同一套日期校验：到**今天**时右箭头自动置灰（未来没有数据），到**90 天前**时左箭头自动置灰，鼠标悬停会说明原因；边界上的箭头点了不会有任何反应，也不会弹「越界」提示。箭头是用 CSS 画的 chevron，不依赖系统字体里的 ‹ › 字形，Windows / macOS 观感一致；它属于工具条，**不会被截进导出的 PNG**。

**为什么历史日期必须换数据源**：实测 `exportAttendance/1.0` 会**忽略** `startDate` / `endDate`，传 11-02、11-05 都返回当前这一刻的实时快照，拿它算历史出勤等于把今天的数据当成昨天。正确来源是风神「[出勤统计](https://aeolus.ele.me/?targetId=54332#/group/schedule/attendance-statistic)」页的「导出明细数据」：

```js
// 一次请求拿回所有骑手 × 时段的明细，返回 xlsx 下载链接
const API_ATT_DETAIL = "https://httpizza.ele.me/xtop/" +
  "xtop.fs.special.examine.exportStatisticsDetail/1.0";
// 入参必须是 teamIds 数组（传 teamId 会报「查询参数错误」）
{ teamIds: [...], startDate: "2026-11-06", endDate: "2026-11-06" }
```

明细 xlsx 每行是「骑手 × 时段」，含 `站点名称`、`骑手ID`、`考勤日期`、`时段`、`是否排班`、`有效在线时长`、`完单量`，另有「全天」汇总行。[`assess.js`](./assess.js) 的 `ASSESS.detailToAttendance(detailSheets, dateStr, XLSX)` 先扫「全天」行取到每人当日的有效在线时长 / 完单量，再把它摊到该骑手每一行，标准成与实时考勤完全相同的 8 列：

```js
["站点名称", "骑手id", "排班状态", "时段",
 "全天有效在线时长", "全天完单量", "时段有效在线时长", "时段完单量"]
```

之后仍由 `ASSESS.build()` 用**同一套口径**计算，只是换了输入源 —— 不另写一套历史口径，避免两边漂移。

**全天达成标记不可信，一律手工判定**：明细表里全天行的「目标完单量 / 目标在线时长」为空，系统给的「是否达成」并不是按运力标准算的。用 2026-11-06 真实明细核对：

| 判定 | 全天有效出勤人数 |
| --- | --- |
| 直接采信系统「是否达成=达成」 | **205** |
| 按「有效在线 ≥6 小时 且 完单 ≥18 单」手工判定 | **224** |

差 21 人。因此 `detailToAttendance()` **根本不输出「是否达成」列**，`build()` 也只认原始时长与完单量：全天走 `DAY_ATTEND_STANDARD = { timeMin: 360, orders: 18 }`，时段走 `PERIOD_DEFS` 各自的 `timeMin` / `orders`。系统标记在任何链路里都不参与计算。

其他行为：

- **站点 ID 必须有**：历史明细接口要求 `teamIds`，页面优先从所选日期 / 今天的运单缓存里收集（0 次额外请求），缓存缺失时只查运单首页（1 次请求）；两者都拿不到会明确提示「请先打开一次考核看板」，不会静默发空数组请求。
- **历史数据不重复拉**：同一日期的排班 / 明细会缓存在内存里，切回来秒回；「立即刷新」强制重拉。历史日期是定稿数据，5 分钟自动刷新会跳过、复选框也会置灰。
- **文案随模式切换**：历史日期的口径说明会写明「取次日定稿的时段明细」「忽略系统的是否达成标记，按 6h / 18 单手工计算」，不再出现「统计中 / 未开始」。
- **导出图用所选日期**：文件名 `风神出勤达成_YYYYMMDD.png`（例如 `风神出勤达成_20261106.png`），标题、副标题、表头日期同步。

> 11-06 历史明细回归：1645 行 / 351 名骑手，全天应排 231、实排 232、有效出勤 224；五个商圈片全天有效出勤 57 / 38 / 44 / 52 / 33 与截图逐格一致，白天 8 个时段与实时快照一致；11-05 另用独立排班 + 明细单独回归，确认不是复用今天的快照。夜宵2 在 22:10 的实时快照里是 0 人，历史定稿为 80 人 —— 这正是「选 T-1 看定稿」的价值。

## 考核看板也能选日期（v3.8.0）

原「考核看板」工具条也有「日期 + ‹ / › 箭头 + 今天 / T-1 + 数据源标签」，可回看最近 **90 天**（含今天），到边界自动置灰。两个页面的日期**各自独立保存**（`wb_assess_date` / `wb_att_date`），在考核看板切到 T-1 不会影响出勤达成页。

### T-1 的取数与 T0 不同

最容易踩的坑：T-1 不是「把今天的快照换个日期标签」。v3.9.0 之后只剩两处数据源要换：

| 数据 | T0（今天） | T-1 及更早 |
| --- | --- | --- |
| 排班 | `exportSchedule/1.0`：T ~ T+1 | 所选日（T）~ 次日（T+1）（实测导出含两天的排班统计，`build()` 按所选日期过滤） |
| 考勤 / 完单 | `exportAttendance/1.0`：当日实时快照（含全天 / 时段完单量） | `exportStatisticsDetail/1.0`（出勤统计 → 导出明细数据）的骑手 × 时段明细，经 `detailToAttendance()` 标准成同款 8 列 |

第二行是硬要求：`exportAttendance/1.0` 实测**会忽略 `startDate/endDate`**，传任何历史日期都返回当前实时快照，所以历史日期必须换接口。历史明细标准化后仍由 `ASSESS.build([], sch, att, 所选日期, XLSX)` 用**同一套口径**计算；全天仍按 6h / 18 单手工判定，不采信系统的「是否达成」标记。

### 历史日期的结果只放内存

- 结果放进**内存 memo**（按 `日期 + 通道`），切回同一天秒回；「立即刷新」强制重拉；
- 关闭 5 分钟自动刷新（定稿数据不会变），工具条复选框置灰；
- 表头、底部数据源、口径说明和 PNG 文件名（`风神考核看板_YYYYMMDD.png`）都用所选日期；
- 不写任何运单缓存（v3.9.0 起也不再读它做业务计算）。

### 加载速度

v3.8.0 时代历史日期要按终态时间整天分页拉运单（11-07 一整天 10529 单 ≈ 117 页 × 1.2s 节流，1–3 分钟）。v3.9.0 改成「排班 + 出勤明细」两个导出请求后，历史与今天都只要 **2–5 秒**。

### 刚过零点查 T-1 的特殊情况

出勤统计的时段明细通常次日才生成：11-08 00:21 导出 11-07 的明细只有表头、**0 行**。这种情况下 `detailToAttendance()` 会明确报「该日期的出勤统计明细尚未生成」，看板把**标二占比 / 考核得分显示「—」**，绝不把空表当成「无人达标」算成满屏 0 分。稍后重试或改查更早日期即可。

> 站点范围：导出接口要求 `teamIds`；页面用记住的 `wb_team_ids_v1`（0 请求），必要时回退旧运单缓存或查 1 页运单识别一次，详见上文「站点范围只识别一次」。实测 `teamIds: []` 会返回「没有该团队的数据权限」。

## 自动更新怎么工作

版本源是仓库根目录的 [`version.json`](./version.json)：

```json
{
  "version": "3.9.0",
  "notes": "本次更新说明",
  "download": "https://github.com/hubiqi/fengshen-ext/releases/download/v3.9.0/fengshen-ext-v3.9.0.zip",
  "published_at": "2026-11-08"
}
```

插件里的 `updater.js`（service worker）会：

| 时机 | 行为 |
| --- | --- |
| 安装 / 每次浏览器启动 / 每 6 小时 | 匿名读取 `version.json`（主源 `raw.githubusercontent.com`，超时/失败自动切 `api.github.com` contents API 备源，两个源都实时无缓存），与当前版本比较 |
| 发现新版本 | 工具栏图标出现红色 `NEW` 角标、风神页面悬浮球出现红标、看板顶部出现蓝色更新条（含版本说明） |
| 点「下载新版 zip」 | 直接下载 Release 里的安装包，并开始 30 分钟的快速磁盘轮询 |
| 新版文件覆盖到插件目录后 | 读到磁盘上的 `version.json` 比运行时新，自动 `chrome.runtime.reload()`，**无需手动去 `chrome://extensions` 点重新加载** |
| 看板「检查更新」按钮 | 随时手动触发一次检查；**无论结果如何都会在看板顶部显示一条反馈**：绿色「已是最新版本 vX · 已成功连接 GitHub（实际命中的域名），远端版本 vY · 检查时间」、蓝色「发现新版本 vX」或红色「检查更新失败：具体原因 · 无法确认是否有新版本（这不代表已是最新）」。不点按钮时也会显示上次检查的简版结论 |

**一个绕不开的限制**：Chrome 扩展运行在沙箱里，不能改写自己的安装目录。所以「检查 / 提示 / 下载 / 重载」全部自动，但**把新版文件放进插件目录**这一步需要你做一次：

1. 在看板更新条点「下载新版 zip」（或手动到 Releases 下载）。
2. 解压，把里面的文件**覆盖**到当初加载的那个插件目录（注意包含 `version.json`，不要套一层子目录）。
3. 完成。插件会在 1 分钟内自动检测并重载；也可以点更新条上的「已覆盖 · 立即生效」马上生效，或到 `chrome://extensions` 点「重新加载」。

> 如果你是通过 Chrome 应用商店安装的扩展，浏览器本身会自动更新，不需要本机制。本仓库面向「加载已解压的扩展程序」的使用方式。
> 仓库是公开的，检查更新**不需要任何令牌**；插件只读取版本号文件，业务数据只在你本机与风神站点之间流转，不会上传 GitHub。

## 发新版本（维护者）

```bash
# 1. 同步版本号、更新说明、下载 URL
node scripts/bump.mjs 3.9.1 "本次更新说明"

# 2. 提交并推送（网络不稳时用 HTTP/1.1 可避开 HTTP/2 Empty reply）
git add -A
git commit -m "release: v3.9.1"
git -c http.version=HTTP/1.1 push origin main
```

推送后 [`.github/workflows/release.yml`](./.github/workflows/release.yml) 会自动：

- 读取 `version.json` 的版本号；若该版本尚无 Release，则把运行时文件打成 `fengshen-ext-vX.Y.Z.zip`；
- 创建 `vX.Y.Z` Release 并附上 zip（版本未变化时重复推送不会重复发版，安全幂等）。

Release 出现后，所有已安装的插件最迟 6 小时内自动发现新版本；点「检查更新」可立即发现。

> 首次在某台机器上用 git 维护本地插件目录时，若本地目录原本不是 git 仓库，可执行：
> `git init && git remote add origin https://github.com/hubiqi/fengshen-ext.git && git fetch origin && git reset --hard origin/main`
> （该命令会用远端内容对齐本地，请先确认本地没有未提交的重要改动。）

## 常见问题

- **看板数字和系统对不上几十单**：v3.9.0 起完单量取自考勤统计，与运单「终态时间」口径存在 <1% 的正常差异（跨零点归日、改派结算）。若需要逐单核对，请用运单口径分支 `ASSESS.build(orders, …)` 复核。
- **换了账号 / 站点变了，看板报「未能识别站点范围」**：点工具条「重识站点」清掉记住的 `wb_team_ids_v1` 重新识别即可。
- **为什么以前经常全量同步**：旧版每 30 分钟无条件做一次全量校准，而自动刷新每 5 分钟一次，等于每半小时重拉当日全部运单；此外接口入库延迟导致「新增行数 === total 增量」不成立时也会降级全量。v3.4.3 已把定时全量换成滚动分片校准，并放宽对账（延迟单保留缓存、水位不推进、下次自动续补，连续 3 次补不齐才全量）。
- **提示的运单总数跟系统不一样 / 是不是把配送失败算进完单了**：没有算进去。看板「实际完单」只统计配送成功，配送失败单（接口 `state=90`）已剔除；进度条和底部统计里的「拉取 N 单」是接口返回的**全部运单**，本来就包含配送失败，所以比系统里的完单数大。v3.3.4 起进度条会直接写出「配送成功 M · 配送失败 F · 实际完单 M」，底部也有拆分。若对比表格里的「实际完单」仍与系统不同，请记下两个数字再排查（系统部分指标用的是「有效完成单」，还会剔除欺诈单，与考核看板口径不同）。
- **标2 人数为什么比系统少 / 改派单算不算完单**：v3.3.6 起骑手完单达标与标2 只算「非人工改派」的配送成功单（`isReassign != 1`），片区「实际完单」列仍含改派单，这是 KPI 第十三条「改派完单量在标1–标5 中剔除」的口径。看板底部会写明剔除单数、达标人数变化与跌破门槛的人数。注意当前接口无法识别「卡餐 / 兜底 / 养老餐改派单可计入完单」这三类例外，一律剔除。
- **怎么判断「没提示新版本」是真的已是最新，还是更新链接不通**：v3.3.3 起点「检查更新」必有结论。**绿色**＝已成功连上 GitHub，并写出命中的域名与远端版本号，此时确实没有新版；**红色**＝两个版本源都没打通，会列出每个源的具体错误，并明确写「这不代表已是最新」。此前版本的「已是最新」提示藏在本该隐藏的更新横幅里，看起来和链路不通完全一样，v3.3.3 已改为独立可见的反馈条。
- **提示「检查更新失败」**：v3.3.2 起主源 `raw.githubusercontent.com` 超时/失败会自动切 `api.github.com` 备源（每个源最多等 8 秒，备源用 `Accept: application/vnd.github.raw+json` 直接取原始 JSON，实时无缓存）；若两个源都被网络拦截，手动到 Releases 页面查看即可，不影响看板取数。
- **为什么不用 jsDelivr 等 CDN 镜像做备源**：它们对 `@main` 有长缓存，发版后仍返回上一版版本号，会让插件误判「没有新版本」。备源必须实时，因此选官方 API。
- **下载 404**：Release 由 GitHub Actions 在推送后自动生成，稍等 1–2 分钟再试；也可在 Releases 页面手动下载。
- **覆盖了文件但没自动重载**：确认 `version.json` 也一起覆盖、且目录就是 `chrome://extensions` 里显示的那个目录；点「已覆盖 · 立即生效」可强制检测。
- **数据看着不对 / 想强制校准**：点工具条「全量重拉」，忽略缓存重新拉当日全部运单并重建缓存。日常刷新仍走增量。
- **每次刷新还是显示「全量同步」**：v3.4.3 起已取消定时全量，正常刷新应稳定显示「增量同步」。若仍显示全量，底部「触发原因」会写明属于哪一类（跨天 / 换商 / 撤单 / 连续 3 次对账未补齐 / 缓存写入失败 / 手动全量重拉）。最常见的是「缓存写入失败」，通常是浏览器禁用了扩展本地存储。
- **时段怎么不全 / 排班里有「凌晨1」「早餐1」但看板没有**：v3.4.1 起时段矩阵按当日排班统计表动态生成，不再写死 7 个班次。11-05 / 11-06 这类排了早班的日期会显示 9 列，10-31 只有 7 列。看板底部会列出本次实际班次与来源；若显示「排班未取到故回退默认 7 班次」，说明排班导出失败，点「立即刷新」重试即可。落在未排班时段（如 02:00–06:00）的完单按约定不计入矩阵，但仍计入「实际完单」。
- **某时段完单量看着偏少**：先对照底部列出的班次清单与排班表。未排班时段的完单不会进矩阵；另外排班表里出现字典未收录的新班次名时，底部会点名提示「未识别班次」，需要把时间区间补进 `assess.js` 的 `PERIOD_DEFS`。
- **点「复制图片」没反应 / 提示生成图片失败**：先确认已安装 v3.4.0 及以上（`capture.js` 在插件目录里），必要时在 `chrome://extensions` 重新加载扩展。若提示「已自动下载 PNG」说明剪贴板被环境拒绝（页面失焦、企业策略、浏览器版本过旧），直接把下载的图片拖进钉钉即可；按住 Shift 点按钮可直接另存为文件。生成过程中按钮会显示「正在生成图片…」，完成后下方会写明是已复制还是已下载。
- **复制出来的图怎么和屏幕上不一样**：这是预期行为。导出固定按 1240px 桌面宽度、2 倍分辨率出图，不受浮层宽度和响应式排版影响，宽表不会换行；工具条、播报区、底部元信息也不属于看板画面，不会被截进去。字体与屏幕一致（见下条）。
- **「出勤达成」里的应排 / 实排 / 有效出勤分别是什么**：应排 = 排班统计「应排人数」，实排 = 排班统计「排班人数」，有效出勤 = 实时考勤里 `排班状态=排班` 且（时段有效在线时长 ≥ 该时段标准、时段完单量 ≥ 该时段标准）的去重骑手数，全天按 6h / 18 单。实排达成 = 有效出勤÷实排，应排达成 = 有效出勤÷应排（可能超过 100%，因为实排本就可能多于应排）。口径详见上面的「出勤达成」章节。
- **夜宵2 显示「统计中」，或全天数字和第二天看到的不一样**：考勤导出是当日实时快照，尚未结束的班次里多数骑手还没跑满时段标准，所以不显示 0% 告警，而是标「统计中 / 未开始」。想要定稿数字，直接在出勤页把日期切到 **T-1**：历史日期走时段明细，是次日定稿数据，不再显示「统计中」（实测 11-06 夜宵2 实时快照为 0 人，历史定稿 80 人）。
- **怎么在出勤页看昨天的达成 / 日期能选多早**：点工具条「T-1」或在日期选择器里挑日期，可回看最近 90 天（含今天）。切到历史日期后数据源标签变绿显示「历史明细」，自动刷新自动停用；「今天」按钮可一键切回实时快照。所选日期会写进表头、底部口径和 PNG 文件名。
- **想一天天往前翻日期，不想每次都开日历**：点日期框两侧的 ‹ / › 左右箭头，一次挪一天，连点可快速翻到任意历史日期；箭头切换和手工选日期走完全相同的校验与数据源。到今天时右箭头、到 90 天前时左箭头会置灰，悬停可看原因 —— 这是正常边界，不是按钮坏了。箭头属于工具条，不会出现在复制出来的 PNG 里。考核看板与出勤达成页都有这组箭头，但日期各自独立、互不联动。
- **怎么在考核看板看昨天的绩效 / 为什么 T-1 第一次要点几分钟**：点工具条「T-1」或日期框两侧箭头。T-1 的运单要按整天「终态时间」窗口全量分页（实测 11-07 有 10529 单 ≈ 117 页，页间 1.2s 节流），所以首次加载约 1–3 分钟，进度条会显示页数；切到别的日期再切回来会秒回。「立即刷新 / 全量重拉」会强制重拉该日。考核口径与今天完全一致，只是把运单、排班、考勤三条数据源都换成该日期的定稿数据。
- **选了 T-1 会不会把今天的增量缓存弄坏**：不会。`wb_orders_current` 是固定单键、只存当天，历史日期完全跳过读 / 写（进度条显示「历史定稿」），结果只放内存。切回「今天」时原来的终态水位与增量链路原样可用。
- **凌晨查 T-1 提示「该日期的出勤统计明细尚未生成」**：出勤统计的时段明细通常次日才生成，刚过零点导出会只有表头 0 行。此时看板把标二占比、考核得分显示「—」，不会把空表算成「无人达标」的 0 分。稍后再点「立即刷新」，或改查更早日期即可。
- **为什么历史日期的全天人数跟系统导出的「达成」列不一样**：系统「是否达成」标记在全天行不是按 6 小时 / 18 单算的（11-06 实测系统判 205 人，按运力标准应为 224 人，差 21 人）。本页完全忽略该列，只用明细里的有效在线时长与完单量手工判定，所以和系统标记不一致是**预期且正确**的。
- **历史日期提示「站点范围为空」**：`exportStatisticsDetail/1.0` 必须带 `teamIds`。先打开一次「考核看板」让它写入当日运单缓存，再回出勤页点「立即刷新」；缓存缺失时本页也会自动查一次运单首页补齐站点 ID。
- **复制出来的图太长 / 不想把出勤达成放进图里**：v3.6.0 起两个入口已经完全分开，原考核看板的 PNG 永远不含出勤达成表，不需要任何开关；出勤页的「复制图片」也只截自己的两张达成表。
- **出勤达成显示「暂不可用」**：说明排班统计或考勤缺关键列（例如旧导出没有 `排班人数`、`排班状态`、`时段完单量`）；历史日期还要求明细里有 `骑手ID / 时段 / 有效在线时长 / 完单量 / 站点名称 / 是否排班`。页面会点名列出缺什么，且不会把空表塞进 PNG。缺「完单量」时会自动降级为只看有效在线时长并标注。
- **字体不好看 / 字太小发虚**：v3.4.2 起统一用系统默认 UI 字体栈（macOS = SF Pro + 苹方，Windows = Segoe UI + 微软雅黑），表格数字启用等宽对齐，中文、西文、数字字形更协调；同时移除了 v3.4.1 在班次变多时给整张表加的 `compact` 小字号（表头最小 10px）。现在无论 7 / 9 / 11 个班次，一级表头 13px、二级表头与完单率 12px、正文 13px 都固定不变，只压缩列宽。`capture.js` 的导出根节点用同一份字体栈，保证 PNG 与屏幕观感一致。
- **权限说明**：`alarms`（定时检查）、`downloads`（下载 zip / PNG）、`clipboardWrite`（复制图片，MV3 无安装警告）、`https://raw.githubusercontent.com/*` 与 `https://api.github.com/*`（主/备版本源）均为自动更新与复制图片所需；`storage` / `unlimitedStorage` 为运单增量缓存所需（数据只存本机，不上传）；`tabs` / `scripting` / `declarativeNetRequestWithHostAccess` 为原有看板取数能力。

## 排班模块（v3.17.0，第四个独立入口）

总按钮菜单里选青色「排班模块」，或面板顶部第四个页签。与考核看板 / 出勤达成 / 运力模块一样是独立页面、独立导出图，互不干扰。

### 数据源：**不新增接口**
仍是三个页面一直在用的 `exportSchedule/1.0`（排班查询 → 导出排班数据）：

| 项 | 值 |
|---|---|
| 接口 | `POST xtop.fs.special.schedule.exportSchedule/1.0` |
| 请求体 | `{ teamIds, startDate: 所选日, endDate: 所选日 + 1 }` |
| 返回 | OSS xlsx，含「排班表」「排班表(行)」「排班统计」三个 sheet |
| 站点范围 | 复用 `wb_team_ids_v1`（考核看板 / 出勤达成记住的 8 个站点）；首次没有时查 1 页运单取 `teamId`。**必须显式传 teamIds**，传空数组会报「没有该团队的数据权限」 |
| 请求量 | 切日期 1 次导出；站点勾选、维度切换、显示方式切换全部本机重算，**0 额外请求** |

`排班统计` 表头：`团队id / 团队名称 / 日期 / 站点人数 / 时段 / 应排人数 / 排班人数 / 预估单量`，含「全天」行。`排班表(行)` 表头：`日期 / 团队id / 团队名称 / 骑手id / 骑手姓名 / 手机号 / 排班`。

### 口径（对齐用户提供的排班查询截图）

- **缺口** = 排班人数 − 应排人数（正数绿色、负数红色、0 灰色）
- **排班率(百分比)** = 排班人数 / 应排人数（可 >100%；≥100% 绿色、<80% 红色、其余默认色）
- **排班率(分数)** = `排班人数/应排人数`，如 `59/56`
- **全天** = 排班统计的「全天」行；**时段列按当日实际排班动态生成**，按 KPI 11 时段顺序排列（凌晨1 / 凌晨2 / 凌晨3 / 早餐1 / 早餐2 / 午高峰 / 下午茶1 / 下午茶2 / 晚高峰 / 夜宵1 / 夜宵2）
- **4排班占比** = 当天排了 ≥4 个班次的骑手数 / 该组「全天」排班人数（从「排班表(行)」按骑手统计，班次串按 `、` 等分隔，排除「休息」「全天」）
- **总计** = 各列求和（4排班占比分子分母分别求和后再算）
- **商圈片**：站点名经 `SITE_TO_AREA` 映射成接口原生商圈片名后再去掉「福州」前缀与「商圈片」后缀，与钉钉看板同一套分组；切「站点」则一行一个站点。
- **「时段排班出勤率」不做**：该指标排班数据里没有，看起来属于实际出勤口径，T+1 的排班查询拿不到，先不放一个假数字。

### 操作

- **日期**：默认 `T+1`（明天），左右箭头逐日快切，可回看 90 天 / 提前 7 天；「今天」「T+1」快捷按钮；结果按日期缓存在内存，「立即刷新」强制重拉。
- **站点选择 (8)**：下拉多选 + 全选 / 取消全选，默认全选；取消全选显示空态，不报错。
- **维度**：「商圈片 / 站点」分段切换（选择记在本机）。
- **显示方式**：默认「全部」——每格三行同时显示缺口 / 百分比 / 分数（对齐桌面宽表）；另有「缺口」「排班率(百分比)」「排班率(分数)」三个按钮可只留一种，窄屏也好读。
- **导出**：`导出 CSV`（UTF-8 BOM，每个时段拆成缺口 / 排班率 / 分数三列，含总计行）、`复制图片`（Shift 点击另存 PNG，画布宽度按内容自适应、不裁右侧列）、`纯净看板`。

## 运力模块表头排序 / 列筛选 / 冻结（v3.18.0）

宽表 22 列横向很长，这一版把「看数」的三种常用操作都做成**纯前端、0 额外请求**：

- **清除排序/筛选**：工具条一键还原，没有排序 / 筛选时按钮自动禁用；状态条实时写明当前排序列、筛选列数与冻结列数。
- **表头冻结**：`thead` 常驻滚动区顶部（容器 `max-height: 72vh`），纵向滚动时表头不动。
- **v3.19.1 滚动修复**：早期版本曾在左右滑动时把滚到冻结区下面的列整列 `visibility:hidden`，但 CSS sticky 下这些列**仍占布局宽度**，于是冻结列右侧出现一大片空白，看起来像丢了几列或数字错位。现已移除该逻辑：22 列始终全部渲染，滚到左边的列由不透明的冻结列自然盖住，表头与数据行逐列对齐；复制图片同样不再需要做可见性还原。
- **自定义冻结左侧列**：工具条「冻结列 (N)」面板列出全部 22 列，可勾选**一列或几列**（建议从左起连续勾选，上限 6 列），选择即时生效并记在 `localStorage.wb_wf_frozen`；默认冻结「站点id ＋ 站点」。冻结列 `position: sticky`，`left` 按真实列宽逐个累加（切月 / 筛选 / 排序 / 改窗口后都会重算），最右一列带边界阴影；表头与冻结列的交叉格层级最高。

- 表头文字仍是纯文本（箭头与漏斗由 CSS 伪元素 / 空按钮绘制），所以 CSV 表头、复制图片里的列名与旧版完全一致。

## 排班模块「时段排班率」与权重配置（v3.19.0）

宽表最后一列新增 **时段排班率**，按手机端「时段权重配置」的公式算，是**由排班数据合成**的指标，不是真实出勤率（排班导出里没有出勤数据）。

- **公式**：`时段排班率 = Σ( min(排班人数 / 应排人数, 100%) × 该时段权重 ) / 100`。完成率上限 100%，多排班不奖励。
- **没有的班次按 100%**：某时段应排人数为 0，或当天排班统计里根本没有这个班次（例如当天只排了 9 个时段），该时段完成率按 100% 计，不会因为缺班次拉低整组分数。
- **默认权重**（对齐截图，11 个时段合计 100%）：凌晨1/2/3、早餐1/2 各 **4%**，午高峰 **30%**，下午茶1/2 各 **7%**，晚高峰 **20%**，夜宵1/2 各 **8%**。截图滚动区只拍到前 9 项（84%），夜宵两项按补足 100% 设为各 8%，可在面板里改。
- **「时段权重」面板**：列出全部 11 个时段，权重 0~100、**支持小数**；实时显示「当前合计」，不等于 100% 时给橙色建议提示（仍可保存）；「恢复默认」一键还原并立即生效，「保存」写入 `localStorage.wb_sch_weights`；非法输入标红并拒绝保存；权重全为 0 时该列显示「—」，不给出误导性的 0%。
- **不自动归一化**：权重合计不是 100% 时，结果按实际合计缩放（与参考系统「建议合计 100%」的提示一致），页面说明与面板都会显示当前合计；总计行按所有站点的总应排 / 总排班逐时段重新加权算，**不是**各组结果求平均。
- **纯前端、0 额外请求**：改权重、切站点、切维度、切显示方式都只在本机重算；只有切日期才重新导出排班。CSV 末尾多「时段排班率」一列，复制图片的画布宽度跟着新列自适应；权重面板挂在 `#sheet` 外，不会出现在导出图里。

## 出勤达成「时段排班率」（v3.20.0）

实排达成、应排达成**两张表末尾都加了「时段排班率」列**（每个商圈片一行、含总计行），顶部概览同时给出整商数值。表格总宽仍锁 1218px：新列固定 112px，其余班次列均分剩余宽度，所以「复制图片」仍是原来的 2480px 宽，不撑破画布。

**公式**：`时段排班率 = Σ( 时段完成率 × 该时段权重 ) / 100`，固定遍历 11 个 KPI 时段（凌晨1/2/3、早餐1/2、午高峰、下午茶1/2、晚高峰、夜宵1/2），与排班模块同名列同一套权重。

| 时段状态 | 完成率 |
| --- | --- |
| 已结束班次 | `min(有效出勤 / 应排人数, 100%)` —— 即「应排达成」口径，与表内格子一致 |
| **T0 未开始 / 进行中班次** | `min(排班人数 / 应排人数, 100%)` —— 按你说的**降级用排班完成率**，不把未来班次误算成 0% 炸班 |
| 当天没有该班次，或应排为 0 | `100%`（与排班模块一致，不因缺班次拉低整组） |

- **两表同值**：实排达成与应排达成的末列用同一套时段完成率加权，切页签不会变；这是「达成口径」的加权值，不是排班模块那个纯排班值。
- **T0 降级范围**：`att.ongoing` 里所有未跑完的班次（含「统计中」与「未开始」）都按排班完成率算；历史日期定稿数据 `ongoing` 为空，全部班次按达成率算。表格里被 `periodsFor()` 隐藏的未结束班次**仍会进入加权**，不会漏项。
- **总计行**用整商逐时段的 `att.totals` 重新加权，不是各商圈片结果求平均；多排班不奖励（完成率封顶 100%）。
- **权重复用**：直接读 `localStorage.wb_sch_weights`，与排班模块「时段权重」面板共用一份配置，默认 11 项合计 100%（4/4/4/4/4/30/7/7/20/8/8）。在排班模块改一次，两个页面通过 `storage` 事件实时同步重算；权重合计不为 100% 时按实际合计缩放（不自动归一化），合计为 0 时显示「—」。出勤达成页不重复做面板。
- **0 额外请求**：新列完全由已取到的排班统计 + 考勤数据算出，改权重、切页签、切日期都本机重算；表头 hover、概览说明、页脚都写明公式与降级口径。

## 自动更新与「热更新」能走到哪一步（v3.20.1）

### 现在已经是半自动闭环

1. Service Worker 每 **6 小时**、浏览器启动、扩展安装/更新时检查 GitHub 的 `version.json`（主源 raw，备源 contents API，8 秒超时自动切换）。
2. 发现新版本 → 看板顶部出现更新条 → 点「下载新版 zip」（`chrome.downloads`，存到系统「下载」目录）。
3. 下载完成后多一个 **「打开下载文件夹」** 按钮（v3.20.1），直接定位 zip，少一步自己翻目录。
4. 把 zip 解压后的文件覆盖到插件目录 → 扩展每 1 分钟自检磁盘 `version.json`，发现版本号比运行时新就 **自动 `chrome.runtime.reload()`**；也可以点「已覆盖 · 立即生效」立刻触发。覆盖后的 30 分钟内保持快速轮询，窗口外恢复 6 小时常规检查。

### 为什么做不到真正的「静默热更新」

| 想法 | 结论 |
| --- | --- |
| 扩展自己下载并写入插件目录 | ❌ MV3 沙箱不允许扩展写自身安装目录 |
| 扩展内 `eval` / 加载远程 JS 实现热替换 | ❌ MV3 CSP 禁止远程代码，`script-src 'self'` 也不允许 blob |
| 用 `chrome.runtime.requestUpdateCheck()` 自动更新 | ❌ 只对 Chrome 网上应用店分发的扩展有效 |
| 自托管 `.crx` + `update_url` | ⚠️ 理论可行，但用户必须改用 `.crx` 安装；macOS / Windows 对非商店 CRX 有额外拦截，开发者模式加载的目录也不会走这条路 |
| Native Messaging / 本机脚本写目录 | ✅ 唯一能全自动的路径，但要额外安装本机程序，代价大于收益 |

所以「检查 / 提示 / 下载 / 覆盖后自动重载」可以全自动，**唯独「把新版文件放进插件目录」这一步必须由用户或本机脚本完成** —— 这是 Chrome 的安全边界，不是插件偷懒。

### 可选：本机一键脚本

如果嫌手动解压麻烦，可以在本机放一个双击运行的 `hot-update.command`：从 `version.json` 读最新版本 → 下载 Release zip → 解压覆盖到插件目录。扩展检测到磁盘版本变化后仍会自动 reload。这条路径不打包进扩展（不需要额外权限），属于本机工具。

## 物资租用（v3.21.0，第五个独立入口）

从 `FengshenMonitor_v2.2` 的「物资租用登记」复刻成独立页面，不依赖原插件、不新增后端，站点 / 物资类型 / 骑手都走原接口。

### 数据源（4 个接口，全部沿用线上）

| 用途 | 接口 | 请求 |
| --- | --- | --- |
| 站点列表 | `xtop.lpd.intelligentConfig.getTeamsAll/1.0` | `{params:{}}` → `result.data[].{id,team_name}` |
| 物资类型 | `...knightRentPizza.queryRentType/1.0` | `{params:{}}` → `result.data[].{id,name}`（当前为电动车 10001 / 住宿 10002） |
| 站点骑手 | `...knightRentPizza.queryTeamKnightInfo/1.0` | `{params:{goodsBusinessRentKnightInfoDto:{teamId}}}` → `result.data[].{teamId,knightId,knightName,mobile}` |
| 租用登记 | `...knightRentPizza.createRent/1.0` | `{params:{goodsBusinessRentCreateDto:{teamId,knightId,categoryList:[{categoryId,startTime,endTime,num}],rentType:2}}}` |

### 口径与操作

- **租用 vs 领用**：租用固定 `rentType: 2`，必须带 `startTime + endTime`，`categoryList` 只需要 `categoryId`；装备领用是 `rentType: 1`、只有 `startTime`、还要 `typeId + categoryId`，本页不做领用。
- **日期边界**：开始日期取当天 `00:00:00`，结束日期取当天 `23:59:59`，按本地时区 `new Date("YYYY-MM-DDT00:00:00")` 计算，避免 `new Date("YYYY-MM-DD")` 被当成 UTC 零点。
- **逐条登记**：站点 → 骑手（可按姓名 / 手机号 / id 过滤下拉）→ 物资类型 → 数量（1~99）→ 起止日期；提交前二次确认，成功 / 失败都会写进「最近提交」。
- **批量登记**：骑手多选列表（搜索、全选当前筛选、清空），每条间隔 **150ms**，逐条显示「已处理 / 成功 / 失败」与进度条；失败原因在汇总里列出前 5 条。
- **本机历史**：`localStorage.wb_rent_history` 保留最近 **100** 条（时间 / 站点 / 骑手 / 物资 / 数量 / 起止 / 成功失败），只用于核对，不代表服务端全部记录。
- **站点记忆**：`localStorage.wb_rent_site` 记住上次站点；切站点只重拉骑手列表，物资类型是全局的。
- **双通道**：直连失败（CORS / 登录态 / 网络）自动切静默桥接，与其它模块一致；工具条可手动切换并记住。
- **安全提示**：提交会真实写入租用单，页面底部与确认框都写明；批量前请先核对骑手与日期。

### 入口

总按钮菜单第五项「物资租用」（橙色图标），独立页面 `rent.html`，也可在悬浮面板页签切换；`sw.js` 的 `PAGE_URL.rent`、manifest 的 `web_accessible_resources`、Release 打包清单都已接入。

## 物资租用：表格导入批量执行 + 本月可绑定（v3.22.0）

### 一、批量执行（表格导入）

「批量登记」卡片右上角的「批量执行（导入表格）」会打开一个弹层，三步走：

1. **下载模板 CSV**：表头固定 7 列 —— `骑手姓名 / 手机号 / 骑士ID / 物资类型 / 数量 / 开始日期 / 结束日期`，附 3 行示例（示例是假骑手，导入时会被判「当前站点没有这位骑手」自动跳过）。
2. **导入**：可选 `.csv` / `.xlsx` 文件，也可以把 Excel 里选中的区域**直接粘进文本框**（制表符分隔也能认）。表头支持别名：姓名 / 手机号码 / 类型 / 件数 / 开始时间 / 结束时间 等。
3. **预览 → 执行**：每行先校验，预览表里逐行给出「可执行」或具体原因，**只有通过的行会被提交**；执行时每条间隔 150ms，逐行回填成功 / 失败，同时写入「最近提交」。

识别与校验规则：

- **骑手**：骑士ID 优先 → 手机号 → 姓名（重名会要求补手机号或 ID），且必须在**当前站点**的骑手列表里，否则报「当前站点没有这位骑手（先切站点）」。
- **物资类型**：写 `电动车` / `住宿` 或直接写 `10001` / `10002` 都行。
- **数量**：留空按 1，必须是 1 ~ 99 的整数（写 0 会被拦下，不会被悄悄改成 1）。
- **日期**：`2026-11-01` / `2026/11/1` / `2026.11.1` / `20261101` / `2026-11-01 00:00:00` / Excel 日期序列号都能认；开始不能晚于结束。
- **重复行**：与前面某行完全一样的（同骑手 + 同物资 + 同数量 + 同起止）会被标成「与第 N 行完全重复，已跳过」，避免一次导入写出两条一样的租用单。
- 一次最多 200 行。

### 二、本月可绑定日期

新增「本月可绑定日期」卡片，按 **人资名单的入职 / 离职时间 × 本月日历** 算出每位骑手哪天可以绑定：

| 状态 | 含义 | 条形颜色 |
| --- | --- | --- |
| 可绑定 | 已入职、未离职、日期 ≥ T-6，且当天没有同类型已有单 | 绿 |
| 已占用 | 当天已被同类型已有租用单覆盖（新单须从该单结束次日起） | 橙 |
| 超出补登期 | 已入职，但日期早于 T-6 | 灰 |
| 未入职 | 日期早于入职日 | 黄 |
| 已离职 | 日期晚于离职日（**离职当日仍算可绑定**） | 红 |

- 数据源：`ehr/staff/knight/list?departmentId=<站点 id>`（`departmentId` 就是站点 `id`），一次拿全该站所有人（含离职），带 `entryTime` / `leaveTime` / `workStatus`；同一骑士多条记录时按 `knightId` 去重，优先在职、其次取最晚入职。
- 默认只列**本月还有可绑定日**的人，按可绑定天数从多到少排；勾「含已离职」会连带本月在职过的离职骑手一起列出。
- **导出日历**：`站点, 骑手姓名, 手机号, 骑士ID, 入职, 离职, 在职状态, 可绑定天数, 可绑定区间` + 本月每天一列。v3.22.0 时是单表 CSV，**v3.24.0 起改为 `.xlsx` 双 Sheet**，见下一章。

## 物资租用：同类型单不重叠 + T-6 可绑定窗口（v3.23.0）

### 一、已有租用单数据从哪来

风神「物资管理 → 物资租用登记」页面（`#/aeolus-goods-rent/index.html`）的「查询」按钮打的是：

```
POST https://httpizza.ele.me/xtop/xtop.knight.task.mng.growth.knightRentPizza.queryList/1.0
{ "params": { "goodsBusinessRentQueryDto": {
    "page": 1, "pageSize": 500, "teamIds": [<站点 id>...], "queryType": 2
} } }
```

- `queryType=2` 是租用记录（`1` 是装备领用）；`teamIds` 支持一次传多个站点，`pageSize=500` 实测可用。
- 返回 `result.data.goodsBusinessRentRecordDtos[]`，带 `knightId / knightName / categoryId / categoryName / rentType / startTime / endTime / status / teamId / teamName`，另有 `total` 用于翻页。
- `startTime / endTime` 是毫秒时间戳，按**本地时区**还原成 `YYYY-MM-DD`（`endTime` 是当天 23:59:59.999，仍算当天）。
- 插件只保留 `rentType=2` 且时间戳有效的记录；切站点 / 点「刷新已有单」会重拉，提交成功后本地立即并入一条，保证同一批导入后面的行能看到刚提交的单。

实测茶亭站 102 张单，**同一骑手同类型的多张单正好首尾相接、不重叠**（如王海涛住宿 10-20~21 → 10-23~29 → 10-30~30），与业务规则一致。

### 二、两条规则

**规则 1：同一骑手 + 同一物资类型的租用单，区间不能重叠。**

- 判定：新单 `[start, end]` 与已有单 `[r.start, r.end]` 只要有公共日期就算冲突，即 `!(end < r.start || start > r.end)`。
- 所以已有 `11-01~11-03` 时，`start=11-03` 仍冲突，**最早只能 `11-04` 开始**。
- 不同类型互不影响（电动车与住宿可以同时租）；不同骑手互不影响。
- 三处提交统一走同一套纯函数：`submitOne` / `submitBatch` / `runImport`；表格导入还会把**批内已计划的行**一起放进冲突池，避免一次导入自己撞自己；执行前再查一次，防止照着过期预览提交。
- 命中时直接**拦下不发请求**，并给出「最早可从 X 开始」——`suggestStart()` 会跳过首尾相接的多张单、保证新单整段放得下、且不早于 T-6。
- 导入弹层有「**重叠行自动顺延**」按钮：一键把所有因重叠被拦的行按各自建议起始日整体平移（保持原有天数），重新校验后由你确认再执行。

**规则 2：可绑定窗口 = T-6 到未来。**

- 入职前、离职后、早于 T-6 的日期都不能绑定；离职当日仍算可绑定。
- 提交侧同样校验：开始日期不能早于 T-6；人资名单取到时，开始不能早于入职日、结束不能晚于离职日（名单取数失败就只查 T-6，不硬拦）。
- 日历按「物资类型」切换占用口径：`全部物资`（任一同类型单占用即不可绑）/ `电动车` / `住宿`。
- 导出矩阵新增「**最早可绑定起日**」「**已有单(本月)**」两列，逐日明细新增「**占用单**」列；「全部站点」导出会同时拉全部站点的已有单。

### 三、状态码与可靠性

- 服务端返回的单目前 `status` 基本都是 `2`，页面把已到期的单显示为「已过期」是根据 `endTime` 与当前时间比较算出来的。插件把查到的记录一律视为占用（保守，宁可多拦），不依赖 `status` 猜测是否作废。
- 已有单只放内存、不写 localStorage，避免隔夜过期；切站点、刷新、点「刷新已有单」都会重新取。取数失败时概览会标「取数失败，占用未生效」。

## 物资租用：导出改 Excel 双 Sheet（v3.24.0）

### 一、为什么要换成 xlsx

v3.22.0 / v3.23.0 的「本月可绑定日期」导出是单表 CSV，用 Excel 打开有三个问题：表头日期列只有 `1 2 3 … 30`，不带年月；`2026-11-05` 这类文本会被 Excel 自动识别成日期、显示成 `2026/11/5`；已有单占用只能写「已占用」，看不到是哪张单。CSV 也没法分工作表。

v3.24.0 把**两个导出按钮都改成 `.xlsx` 工作簿**，并且不再提供 CSV 版（导入模板仍是 CSV，那个是给「批量执行」用的，与导出无关）。

### 二、工作簿结构

固定两个 Sheet：**「租车」**（电动车 `10001`）与 **「住宿」**（`10002`）。两张表不是同一份数据复制两遍，而是**各自只按本类型的已有租用单判占用**，所以同一个人的「可绑定天数 / 可绑定区间 / 最早可绑定起日 / 已有单(本月)」在两张表里会不一样。页面上「物资类型」下拉只影响页面日历，**不影响导出**——导出始终给两个 Sheet。

| 导出按钮 | 文件名 | 每个 Sheet 内容 |
| --- | --- | --- |
| 导出日历 Excel | `物资可绑定_<站点>_<年-月>_日历.xlsx` | 11 列基础信息 + 本月每天一列，一人一行 |
| 导出逐日明细 Excel | `物资可绑定_<站点>_<年-月>_逐日明细.xlsx` | 站点 / 姓名 / ID / 手机号 / 日期 / 星期 / 状态 / 占用单 / 说明，一人一天一行 |

### 三、表头与「已绑定」

- **日期表头写完整年月日**（如 `2026-11-01`），不再只写日号。所有单元格都用 `inlineStr` 文本写入，Excel 不会做日期转换，骑士 ID 也不会变成科学计数；中文不需要 BOM。
- **已绑定的格子写两行**：第一行 `已绑定`，下一行直接列出占用该日的租用单（如 `住宿 11-08~11-08`），最多列 2 张、多于此显示 `…`。日期缩成 `MM-DD` 避免撑爆列宽，单元格开了自动换行。
- 状态标签统一：可绑定 / 已绑定 / 超出补登期 / 未入职 / 已离职。页面图例、导入弹层、导出表都用同一套文案。
- 单元格按状态上底色：可绑定绿、已绑定橙（加粗）、超出补登期灰、未入职黄、已离职红；表头深灰底白字；**冻结首行 + 左侧 11 个信息列**（明细冻结前 4 列），并带自动筛选。
- 逐日明细里「已绑定」行会带出「占用单」详情；不勾「含已离职」时只导「可绑定 / 已绑定」两种日期。

### 四、实现：零依赖 xlsx 读写器

`xlsx.js` 从纯读取器扩成**读写器**：

- 读侧 `XLSX_READER`（v3.22.0 已有）：解析 ZIP 中央目录，`DecompressionStream("deflate-raw")` 解压，DOMParser 读 sharedStrings / worksheet，给「表格导入」用。
- 写侧 `XLSX_WRITER`（v3.24.0 新增）：`store`（不压缩）ZIP + 表驱动 CRC32，拼出 `[Content_Types].xml` / `_rels/.rels` / `xl/workbook.xml` / `xl/_rels/workbook.xml.rels` / `xl/styles.xml` 与两张 `sheetN.xml`。不引入 SheetJS、不用 eval、不请求远程资源，MV3 可直接打包。
- 单元格用 `inlineStr` + `xml:space="preserve"`，换行写 `\n` 配合 `wrapText`；样式表定义 8 组 `cellXfs`（默认 / 表头 / 信息列 / 五档状态色）。
- 生成的是标准 OOXML，Excel / WPS / Numbers 都能直接打开；本机用 `unzip -t` 与 `XLSX_READER` 双向校验过（结构、中文、换行、两个 Sheet 名）。

## 物资租用：按金额反算登记（v3.25.0）

给某位骑手扣一笔钱时，不用再手算「要登记几天、数量填几」。新增卡片里只填**骑士ID + 金额**，插件自动生成起止日期与数量，并先给出可勾选的预览清单。

### 一、口径

| 步骤 | 公式 / 规则 |
| --- | --- |
| 日扣款 | `月扣款 ÷ 当月实际天数`（月扣款按物资类型在页面上填，本机记住；默认 1000 元/月）。例：11 月 30 天 → 33.33 元/天次 |
| 目标天次 T | `⌊金额 ÷ 月扣款 × 当月天数⌋`，向下取整。例：300 元 → `⌊300/1000×30⌋ = 9` |
| 可绑定窗口 | 该骑手该类型从**最早可绑定日**（`max(T-6, 入职日)`，并跳过前置的已绑定 / 离职后日期）到**今天 T0** 的第一段连续可绑日期；T-6 到 T0 最多 7 天。不取未来，遇到已绑定日即截止（一张单的日期必须连续） |
| 匹配 | `天数 d` 从窗口最大天数往下降、`数量 q` 从 1 往上升，取**第一个** `\|T − d×q\| ≤ 1` 的组合；`d×q > T+1` 时提前剪枝（对应「误差变大就减少天数」）。数量上限 99 |
| **金额封顶** | 余量 = 封顶 − **本月已绑**（该骑手本月已有租用单的天数 × 日单价）。单项封顶（默认 500 元）按本类型算，合计封顶（默认 1000 元）按「住宿 + 租车」一起算；本行预计扣款超出更紧的那个余量就**直接拦下**。两个值页面可改、本机记住，填 `0` 表示不封顶 |
| 误差 | 允许 ±1 天次，即金额误差最多约 1 个日扣款。预计扣款 = `d×q × 日扣款` |

两个例子（与页面实现一致）：

- `T=20`、`最大 7 天`：`7×1=7`（差13）→ `7×2=14`（差6）→ `7×3=21`（差1 ✓）→ **7 天 × 3**。
- `T=9`、`最大 7 天`：`7×1=7`（差2）→ `7×2=14`（差5，变大即剪枝）→ 减天数到 `6×2`、`5×2=10`（差1 ✓）→ **5 天 × 2**。

### 封顶怎么算（v3.25.0 起，v3.25.1 改为按「本月已绑」扣余量）

- **已绑** = 该骑手在本月已有租用单里的天数（只取本月区间，跨月自动裁剪），按类型分别累加；**折金额** = 天数 × 该类型日单价（该类型月扣款 ÷ 当月天数，没配过就按默认 1000 元/月）。
- 例：张三本月住宿 1~3 号（3 天）、电动车 5~7 号（3 天），月扣款均 1000（日单价 33.33）
  → 住宿已绑 3 天 ≈ ¥100、电动车已绑 3 天 ≈ ¥100、合计 6 天 ≈ ¥200。
- **余量**：单项余量 = `单项封顶 − 本类型已绑金额`（500 − 100 = ¥400）；合计余量 = `合计封顶 − 两类已绑合计`（1000 − 200 = ¥800）。两个余量取更紧的那个，再换算成天次上限 `⌊余量 ÷ 日单价⌋`（400 ÷ 33.33 = 12 天次）。
- 目标天次 > 天次上限时**先判封顶余量再谈匹配**，直接给「需扣 ¥500（15 天次）超过封顶余量：本月电动车已绑 3 天 ≈ ¥100.00，住宿+租车合计 6 天 ≈ ¥200.00，只剩 ¥400.00（≈12 天次），请调小金额或分多次登记」——不会先算出装不下的方案再反悔。
- 匹配时把天次上限带进 `planDeduction(target, maxDays, qtyMax, maxTotal)`，即使 ±1 容差也会被上限切断，不会「误差对上了但钱超了」。
- 执行前按**当下的**封顶与**最新的**已有单重算余量：预览通过后你把封顶改小、或前一条刚提交成功（已绑变多），点执行同样会被拦下。
- 预览新增两列：**「本月已绑」**（本类型：天数 / 金额，如 `3 天 / ¥100.00`）与**「本月合计」**（住宿 + 租车）。被拦下的行也照常显示已绑，方便判断是不是这个月已经扣过。
- 实测口径（月扣款 1000、11 月 30 天）：无已绑时 `¥300 → 5天×2=10 天次 ≈ ¥333`（放行）、`¥520 → 7天×2=14 ≈ ¥466.67`（放行）、`¥550 → 16 天次`（超 15 上限拦下）、`¥2000 → 60 天次`（拦下，提示只剩 ≈15 天次）；已绑 3 天 ¥100 时 `¥400`（12 天次）刚好放行、`¥500`（15 天次）被拦。

### 二、输入与预览

- 一个文本框，每行 `骑士ID 金额`（空格 / 逗号 / 制表符分隔，可直接粘 Excel 两列；金额可带 `¥` / `元`）；`#` 开头是注释，空行跳过。**同一骑士 ID 出现多行时金额合并成一张单**，避免自己撞自己。
- 物资类型整批统一选，月扣款按类型分别记忆。顶部实时显示「按 2026-11（30 天）折算 · 日扣款 33.33 元/天次」。
- 预览表逐行给出：目标天次、最早可绑、起止日期、天数、数量、实际天次、误差、预计扣款、状态。金额太小 / 骑士ID 不在当前站点 / 没有可绑窗口 / 匹配不到解，都会写明原因并自动取消勾选。
- 只执行勾选且通过校验的行；**提交前二次确认**，执行时再校验一次（名单、已有单可能已变），每条间隔 150ms，成功后本地并入已有单池并写「最近提交」。

### 三、边界与分层

- 窗口里若已有单占满到今天之后，或入职日晚于今天，会明确提示「没有可绑定的连续日期 / 最早可登记日晚于今天」，不硬凑一张会重叠的单。
- 目标天次过大（超过 `最大天数 × 99`）时提示匹配不到，而不是把数量写成 100 以上。
- 代码按三层放：`deductTarget / deductWindow / planDeduction / planDeductRow / planDeductRows / parseDeductInput` 是**不碰 DOM 的纯函数**（可直接单测）；`generateDeduct / renderDeduct / runDeduct` 是控制器，只做输入解析、渲染与编排；提交仍走既有的 `postApi + payloadOf + addLocalRent + pushHistory` 通道。
- 「按金额反算」与 v3.23.0 的防重叠规则共用同一份 `state.rents`；生成时窗口已跳过已绑定日，执行时还会再跑一次 `checkOverlap`，不会出现同骑手同类型区间重叠。
